## 1. 硬约束（不可协商）✅

| 编号 | 约束 | 架构含义 |
|---|---|---|
| C1 | **没有自建服务器** | 必须使用托管 BaaS 或 Serverless，不自运维后端进程；**允许部署 Serverless 云函数**（非自建进程，见 ADR-064） |
| C2 | **电脑不保证开机** | 电脑只能作为普通客户端，**绝不能**承担服务端/中转角色 |
| C3 | **两端需数据同步** | 云端作为唯一真相源（Single Source of Truth） |
| C4 | **单人开发** ✅ | 技术选型优先复用率与运维成本 |
| C5 | **目标市场中国大陆** ✅ | 云服务需国内可直连 |

### 由 C1 + C2 推导出的架构基调

```
┌──────────┐                    ┌──────────┐
│ 手机 App │                    │ 电脑 App │
│ 本地库    │                    │ 本地库    │
│ 待发队列  │                    │ 待发队列  │
└────┬─────┘                    └────┬─────┘
     │   各自独立连云，互不依赖          │
     └───────────┬───────────────────┘
                 ▼
      ┌──────────────────────┐
      │  托管云（免费额度）      │
      │  数据库 + 文件存储       │
      │  ★ 唯一真相源           │
      └──────────────────────┘
```

**三条铁律**：
1. 电脑永远不是服务器 —— 关机即下线，与手机地位平等。
2. 两端不直接通信 —— 各自与云端对账，不关心对方是否在线。
3. 云端负责中转与存档 —— local-first，离线是一等公民。

## 2. 架构原则 ✅

| 原则 | 说明 |
|---|---|
| Local-first | 本地写入先成功，同步后置，网络异常不阻塞交互 |
| 客户端生成 ID | 使用 UUID，离线也能创建记录 |
| 软删除（墓碑） | 删除仅置标记，防止离线端把已删数据推回 |
| 乐观锁 | 用 version 字段做并发检测（**挂在文档上**，见 5.6） |
| 时间戳分层 | 文档级 `version` / `updated_at` 由**服务端**生成；记录内 `created_at` / `updated_at` 允许**客户端**生成本地时间（离线可写），详见 4.0 |
| 幂等写入 | 每次操作带唯一 `tx_id` / `capture_id`，重试不产生重复 |
| 跨文档变更原子化 | 一次业务操作涉及多份文档时，**必须**走云函数事务提交（见 5.9 / ADR-050） |
| 状态可见 | UI 必须暴露同步状态与冲突 |

### 2.1 双端"互联"的真实含义 ✅

**必须先纠正一个常见误解**：

> **手机与电脑之间不存在任何直接连接。** 两端互不感知对方存在，各自独立与云端通信。

```
手机 ──→ 云端 ←── 电脑
  ↑                 ↑
  └── 谁也不理谁 ────┘
```

**数据流转路径**：
```
手机改数据 → 推送云端（projects.json v43）
                    ↓
电脑打开/轮询 → 发现 v43 > 本地 v42 → 整体替换本地 → 刷新 UI
```

| 好处 | 说明 |
|---|---|
| 电脑关机不影响手机 | 手机只与云端对话 |
| 无需内网穿透 | 无 NAT 打洞、无公网 IP 需求 |
| 无需两端同时在线 | 各自连过云即可 |
| 无长连接管理 | 无需心跳、重连、连接状态机 |

**推论**：P2P / 局域网直连**不作为基线能力**。它解决的问题（两端都关机时的传输）
在「各自连云」模型下并不存在。

> 若将来确需引入直连作为加速手段，**铁律**：
> 直连只用于加速**读取**，所有**写入**仍统一走云端并经过版本号校验。
> 否则会产生「直连写入 + 云端同步」的双写冲突。

### 2.2 跨端契约一致性 ✅

**本项目最大的隐性风险**：两端必须对同一份 JSON 达成完全一致的理解，
而任何差异都**不会报错，只会静默损坏数据**。

| 契约项 | 强制要求 | 违反后果 |
|---|---|---|
| 日期格式 | 统一 `"YYYY-MM-DD"` | 字段污染、比较失败 |
| 时间戳 | 统一 int64 毫秒，不用浮点 | 精度丢失、排序错乱 |
| 空值表示 | 统一为 `null`，不省略 key | 语义歧义 |
| 枚举值 | 统一小写字符串（`"standard"`） | 类型字段全乱 |
| UUID | 统一小写、带连字符 | 记录匹配不上 |
| 字节序 / 编码 | 统一 UTF-8 | 中文乱码 |

> **措施（v13 调整）**：维护一份**跨端 JSON 契约样本**（同一份数据文件），
> 执行「读入 → 写出 → 逐字节比对」的**序列化回归测试**。
> 8.1 已裁定**单实现 Flutter 双端**（ADR-031），双实现分叉风险随之消失，
> 因此该测试由「必过门禁」**降级为推荐**（ADR-028 已被取代）。
>
> ⚠️ **新增约束（v13）**：云函数必须把 `payload` 当作**不透明 JSON** 存取，
> **不得解析业务字段**（只读 `version` / `updated_at` / `last_tx_id`）。
> 否则 Node.js 侧就成了第二份实现，静默分叉的风险立刻回来。

### 2.3 同步层必须保持单一实现 ✅

推论：**同步层与数据层禁止多实现**。它们承载的隐性契约最多：

- 409 冲突处理与跨文档事务重放（5.9）
- 版本号回退保护（文档级 CAS）
- 墓碑骨架化 / 彻底删除的时机与范围（4.10）
- 级联删除与级联归档的树遍历
- JSON 序列化一致性

若电脑端采用独立技术栈（如 WPF），这些逻辑将被复制两遍，
且两遍之间的差异**不会通过任何测试暴露**。

## 3. 产品定义（当前采用）✅

### 3.1 定位

一款**个人生活管理工具**，用于同时承载两类心智活动：

| 板块 | 心智活动 | 特征 |
|---|---|---|
| **板块一：项目与灵感** | 记录琐碎灵感 + 组织成项目 | 自下而上，先有素材再收拢 |
| **板块二：事件与任务线** | 理清事务进展与安排 | 自上而下，先有事件再展开 |

两个板块**结构同构**（都是节点 + 层级 + 时间），但**语义与交互不同**。

### 3.1.1 双端定位差异 ✅

已确认：手机端与电脑端**有侧重**，而非功能对等。

| | 手机端 | 电脑端 |
|---|---|---|
| **主场景** | 速记、查看进度、勾选完成 | 深度编辑、整理结构、并排对照 |
| **灵感捕获** | ★★★ 系统级入口（小组件/通知栏） | ★★ 应用内快捷输入 |
| **项目编辑** | ★ 简单修改 | ★★★ 长文本、结构调整 |
| **任务树** | ★★ 查看 + 勾选 | ★★★ 拖拽重排、批量整理 |
| **输入方式** | 短文本、语音输入法 | 键盘、鼠标、多窗口 |

> ⚠️ **关键约束**：侧重 ≠ 功能缺失。两端**都能访问全部功能**，只是**导航权重与首屏不同**。
> 否则用户会遇到"手机上看到一个问题却改不了"的挫败感。
> 架构含义：**同一份业务逻辑与同步层，两套 UI 外壳**（见 6.2）。

### 3.2 板块一：项目与灵感（对应目的 1）

**能力**
- 创建 / 删除 / **归档**「项目」
- 项目内容包含三个要素：**目的**、**实现**、**日期**
- 「实现」部分可包含**子项目** → 项目支持**嵌套**
- 项目状态为**三态**：待办 / 已完成(绿) / 忽略(灰)
- 独立入口：**记录灵感**（快速捕获）
- 灵感可**分配到**指定项目下记录
- 灵感与项目可**合并**（时机由用户决定，方式类似 `git merge`）

**灵感的生命周期** ✅（已定，v13 补正入口）
```
① 捕获       灵感创建，status=pending ──→ 出现在「灵感列表」
② 分配       绑定到某个项目 ──────────→ 出现在该项目下（仍留在灵感列表，见 4.12）
③ 合并       上下分区编辑 → 保存 ─────→ status=merged，从灵感列表消失
④ 追溯       merged_into + 完整原文 ──→ 在归档区「已合并」中撤销，可回退为 pending
                    （灵感亦可是 discarded：进入归档区「已丢弃」，可恢复）
```
> **注意**：③ 是「吸收」而非「引用」，灵感列表会变干净。
> **「归档」是本项目的核心保护机制** —— 合并后的原文被完整保留，
> 因墓碑/全量 items 保留完整对象（见 5.3），④ 的成本极低，无需额外的快照表。
> **但撤销合并只恢复灵感本身，不回滚项目正文**（ADR-057，见 4.8）。
> 合并的具体交互见 **4.8**；所有"消失"的入口见 **4.10 归档区**。

**关系结构**
```
项目 A
├── 目的
├── 实现
│   ├── 子项目 A1
│   └── 子项目 A2
└── 日期
    └── 灵感（分配而来 / 直接记录）
```

### 3.3 板块二：事件与任务线（对应目的 2）

**能力**
- 创建 / 删除 / 归档「事件」
- 每个事件是**一条任务线的根**（自身无时间、无描述，见 4.2）
- 从起点**向后连线**引出一个个**标准任务** —— 它们是**同级兄弟链**，由 `order` 决定先后
- 任务分三类：**标准任务**（主线）、**子任务**（附属分解）、**并列任务**（分叉）
- 每个任务可设置**到期 / 目标日**（`due_at`，可空）；完成时会记录 `completed_at`

**关系结构**
```
事件（起点）
   └─→ 任务 1（标准）──→ 任务 2（标准）──→ ...
          └─→ 子任务 1-1        （与任务 1 同框）
          └─⇢ 并列任务          （独立成框 = 分叉，也可带自己的子任务）
```

**完成规则** ✅（已定，详见 4.6）
> 与板块一**完全一致**：节点为三态 `pending / done(绿) / ignored(灰)`，
> **所有"参与判定"的直接子节点都处于终态后，父节点才可被标记为完成**
> （墓碑与归档节点不参与判定，且已完成的父节点会在子节点退回时**自动退回**）。

**节点呈现** ✅（已定，详见 4.9）
```
┌─────────────────────────────┐
│ ■ 任务 1                     │  ← 主任务与其子任务同框
│   └ ☑ 子任务 1-1             │
└─────────────────────────────┘
┌──────────────┐  ┌──────────────┐
│ ■ 并列任务 A  │  │ ■ 并列任务 B  │  ← 各自独立成框
└──────────────┘  └──────────────┘
```

## 4. 数据模型 ✅

> 状态：**核心字段已全部冻结**。以下为可直接落地的 JSON 结构。

### 4.0 通用约定

| 约定 | 规则 |
|---|---|
| 时间戳（文档级） | `version` / `updated_at` 由**服务端**生成，用于 CAS 与冲突判定 |
| 时间戳（记录级） | `created_at` / `updated_at` / `completed_at` 为毫秒整数，**由客户端生成**（本地时钟，离线可写）；服务端只存储、不重写（ADR-067） |
| 日期字段 | ISO 日期字符串 `"YYYY-MM-DD"`，**由用户本地日历选择，不涉及时区** |
| ID | UUID v4，**由客户端生成**，离线可创建 |
| 删除 | 置 `deleted: true`，不做物理删除；**彻底删除 = 墓碑骨架化**（见 4.10） |
| 排序 | 树内兄弟节点用 `order` 整数，间隔 1000，便于中间插入；间隙耗尽时对同父节点整体重编号（见 4.11） |

### 4.1 实体清单

| 实体 | 所属板块 | 中文名 | 结构 |
|---|---|---|---|
| **Inspiration** | 一 | 灵感 | 扁平列表 |
| **Project** | 一 | 项目 | 树（支持嵌套子项目） |
| **Event** | 二 | 事件 | 扁平列表（任务树的根） |
| **Task** | 二 | 任务 | 树（三类任务共用） |

### 4.2 各实体字段

**Inspiration（灵感）**
```json
{
  "id": "uuid",
  "text": "随手记的内容",
  "project_id": null,
  "status": "pending",
  "merged_into": null,
  "merged_at": null,
  "created_at": 1735000000000,
  "updated_at": 1735000000000,
  "deleted": false
}
```
- `project_id = null` → 未分配，留在灵感列表
- `project_id = 某项目` → 已分配，显示在该项目下
- `status` 三态：
  - `pending` 待处理 —— 正常显示在灵感列表
  - `merged` 已合并 —— 从列表消失（被吸收进项目）；入口在归档区「已合并」，可撤销合并（4.8 / 4.10）
  - `discarded` 已丢弃 —— 用户主动放弃，从列表消失；入口在归档区「已丢弃」，可恢复为 `pending`
- 合并采用**屏幕上下分区编辑**（见 4.8），不是 git 式左右对比
- **无 `order`、无 `archived`**：排序与列表归属规则见 4.12

**Project（项目）**
```json
{
  "id": "uuid",
  "title": "项目名",
  "purpose": "目的：为什么做这件事",
  "implementation": "实现：怎么做",
  "date": "2025-12-31",
  "status": "pending",
  "archived": false,
  "parent_project_id": null,
  "order": 1000,
  "completed_at": null,
  "created_at": 1735000000000,
  "updated_at": 1735000000000,
  "deleted": false
}
```
- `date` 为**单个日期**，表示截止日 / 目标日，**允许留空**（`null`）
- `status` 为**三态**：`pending` 待办 / `done` 已完成（绿） / `ignored` 忽略（灰）
  - 语义见 4.6 完成规则
- `completed_at`：被标记为 `done` 时写入；退回 `pending` 或改 `ignored` 时置 `null`（ADR-058）
- `archived` 归档标记，见 4.7
- `parent_project_id` 构成子项目嵌套（**深度上限 3 层**，见 4.11）
- ⚠️ **`collapsed` 已从模型中移除**：折叠等视图偏好不属于数据，改存本地 `ui_prefs.json`，**不参与同步与版本**（ADR-059）
- 灵感的正文内容**不冗余存储**在项目里，通过 Inspiration 的 `merged_into` 反向关联

**Event（事件）**
```json
{
  "id": "uuid",
  "name": "事件名",
  "status": "pending",
  "archived": false,
  "order": 1000,
  "completed_at": null,
  "created_at": 1735000000000,
  "updated_at": 1735000000000,
  "deleted": false
}
```
- 承载**三态**：`pending` / `done`（🟢绿） / `ignored`（⚪灰），与 Project / Task 一致
- 支持**归档**（`archived`）；归档事件 → **整条任务线级联归档**（4.7）
- `completed_at`：同 Project（ADR-058）
- **无时间、无描述** —— 它的唯一职责是充当一条任务线的根节点
- 完成条件：**所有"参与判定"的顶层任务**（`parent_task_id = null`，且未删除、未归档）处于终态（见 4.6）

> ⚠️ **修正记录**：ADR-017 原为「事件仅有一个名字，无时间、无描述、**无状态**」。
> 经 Q54 裁定，事件**纳入三态体系并可归档**，故新增 `status` 与 `archived`。
> ADR-017 的「无时间、无描述」部分仍然有效。

**Task（任务）**
```json
{
  "id": "uuid",
  "event_id": "所属事件ID",
  "parent_task_id": null,
  "task_type": "standard",
  "title": "任务名",
  "due_at": "2025-12-31",
  "status": "pending",
  "archived": false,
  "order": 1000,
  "completed_at": null,
  "created_at": 1735000000000,
  "updated_at": 1735000000000,
  "deleted": false
}
```
- `task_type`：`standard` 标准任务 / `subtask` 子任务 / `parallel` 并列任务
- `parent_task_id`：构成树；**`null` + `order` 升序 = 该 Event 下的主线（兄弟链，见 4.4）**
- `status` 三态（与 Project / Event 统一）：`pending` / `done`（🟢绿） / `ignored`（⚪灰）
- `archived`：支持归档（依据 ADR-041 的统一性原则），归档任务级联其子任务
- `completed_at`：同 Project（ADR-058）
- `due_at`：**到期 / 目标日**（单点、可空），仅作提醒与逾期标记，**不联动任何其他任务**
- 三类任务字段完全一致，仅 `task_type` 与 UI 呈现不同；**允许的父子组合见 4.4（v13 收敛，ADR-053）**
- **并列任务同样可以拥有子任务**（见 4.9）

### 4.2.1 字段一致性 ✅（架构闭合状态）

| 字段 | Project | Event | Task | Inspiration |
|---|---|---|---|---|
| `status` | ✅ 三态 pending/done/ignored | ✅ 同左 | ✅ 同左 | ✅ 三态 pending/merged/discarded<br>⚠️ **独立枚举**：不复用树形实体的状态机（ADR-038） |
| `archived` | ✅ | ✅ | ✅ | — |
| `deleted` | ✅ | ✅ | ✅ | ✅ |
| `completed_at` | ✅ | ✅ | ✅ | — |
| `order` | ✅ | ✅ | ✅ | —（灵感按 `created_at` 倒序，见 4.12） |
| 父引用 | `parent_project_id` | —（任务线的根） | `parent_task_id` + `event_id` | `project_id` |
| 视图状态 | `collapsed` **已移出模型** → `ui_prefs.json`（ADR-059） | — | — | — |

> **结论（v13 修正）**：`Project` 与 `Task` 是**树形实体**；`Event` 是**扁平列表**（任务线的根集合，见 4.1）。
> 三者共用同一套**状态机、完成判定、归档、级联删除/归档**实现；
> **树操作（父引用遍历、移动、重排）只在 `Project` 与 `Task` 上复用**。
> 这是 ADR-039 / ADR-041 带来的实现红利 —— **状态与生命周期三处复用，树操作两处复用**。
>
> ⚠️ `Inspiration.status` 与三态树形实体**同名不同义**：它表达的是「灵感被处理的方式」，
> 不参与完成判定。解析与校验必须按实体类型分开处理，**禁止共用同一个枚举解析器**。

### 4.3 结构裁定结果 ✅

| 编号 | 原歧义 | 裁定 | 架构后果 |
|---|---|---|---|
| A1 | 「并列任务」的语义 | **同级分叉**，互不依赖 | 数据是**纯树**，无环路风险 |
| A2 | 任务完成时间 | **单点**（可空） | 无需区间字段 |
| A3 | 完成时间是否联动 | **不联动**，仅提醒 | **无排期引擎** |
| A4 | 灵感合并是否消耗本体 | **被吸收**，从列表消失 | 必须有快照与撤销路径 |
| A5 | 两板块是否互通 | **暂不互通** | 底层预留统一节点抽象 |
| A6 | 主线（标准任务）之间是父子还是同级 | **同级兄弟链**（`parent_task_id = null` + `order`） | 主线不再嵌套，见 4.4 / ADR-053 |
| A7 | 灵感合并 / 丢弃 / 删除后的入口 | **归档区**统一收纳（4.10） | 「消失」必须有唯一去处与后悔药 |

### 4.4 任务树结构 ✅

```
Event（仅一个名字）
 │  主线：Event 的直接子节点（parent_task_id = null），按 order 升序排成一条链
 │
 ├─ Task(standard) 标准任务 ①
 │     └─ Task(subtask)   附属分解（叶子）
 ├─ Task(standard) 标准任务 ②
 │     ├─ Task(subtask)   附属分解（叶子）
 │     └─ Task(parallel)  分叉，独立成框
 │           └─ Task(subtask)  ★ 并列任务同样可拥有自己的子任务
 └─ Task(standard) 标准任务 ③
```

**主线定义（v13 修正，ADR-053）**：
> 主线 = 同一 `event_id` 下、`parent_task_id = null` 的 `standard` 任务，按 `order` 升序组成的**兄弟链**。
> 标准任务之间**不是父子关系** —— 因此完成标准任务①不会因为标准任务②未完成而被约束；
> `order` 只表达**先后次序**，不构成依赖（A3「不联动」仍然有效）。

**允许的父子组合（v13 收敛）**：

| 父节点 | 允许的子节点 | 说明 |
|---|---|---|
| `Event` | `standard` | 主线的入口 |
| `standard` | `subtask` / `parallel` | 附属分解 / 分叉 |
| `parallel` | `subtask` | 分叉下的分解 |
| `subtask` | ❌ 不允许有子节点 | 叶子 |

> ⚠️ **修正 ADR-040**：`task_type` 仍是**渲染提示**（三类共用同一 schema，ADR-008 不变），
> 但**允许的父子组合受上表约束** —— 不再允许「任意节点拥有任意类型的子节点」。
> 越界数据（历史遗留或异常写入）**按 `subtask` 渲染并记录日志，不崩溃**。

> **重要简化**：由于 A3 裁定为「不联动」，任务之间**不存在依赖边**。
> 这意味着任务线是**树**而非**有向无环图**，同步与冲突处理的复杂度下降一个量级。
>
> **深度上限**：任务树最多 **3 层**（不含 Event），见 4.11。

### 4.5 删除语义 ✅

已确认采用**级联删除 + 二次确认**。

| 操作 | 行为 |
|---|---|
| 删除项目 | 该项目 + 全部子项目 + 其下 `status=pending` 的灵感 → 全部 `deleted:true` |
| 删除项目（已合并的灵感） | `status=merged` 的灵感**不删除**：回退为**未分配 `pending`**，正文回到灵感列表（ADR-056） |
| 删除任务 | 该任务 + 全部子任务 → 全部 `deleted:true` |
| 删除事件 | 该事件 + 它整条任务线 → 全部 `deleted:true` |
| 删除灵感 | 仅该灵感 |

**实现要点**：
1. **级联在客户端完成**：遍历树收集 `id` 集合，批量置墓碑
2. ⚠️ **跨文档时必须走事务提交**：删除项目会同时改 `projects.json` 与 `inspirations.json`，
   **必须**经云函数事务一次提交（5.9 / ADR-050），**禁止**退化为两次独立 PUT
3. **二次确认必须显示影响范围**，例如：
   `「删除项目 A」将同时删除 3 个子项目、7 条灵感。确认？`
4. **墓碑保留完整对象**（见 5.3），因此普通删除是可撤销的（恢复入口在归档区「回收站」）
5. **不做服务端级联**：同步是文档级整包，云函数只做不透明 JSON 存取，不了解树结构
6. **删除 ≠ 彻底删除**：普通删除只置墓碑并进入回收站；**彻底删除**只能在归档区执行，
   需二次确认，且会把墓碑骨架化（见 4.10 / ADR-052）

> ⚠️ 与 4.4 的关系：级联删除**沿树向下**，不涉及依赖图遍历，实现是简单的深度优先收集。
> 墓碑节点**不参与**父节点的完成判定（见 4.6 判定域）。

### 4.6 完成规则 ✅

**问题背景**：项目有子项目，子项目可能"不做"。若无"忽略"状态，
一个不想做的子项目会**永久阻塞**父项目的完成。

**裁定**：项目具备**三态**，而非布尔值。**该规则同样适用于第二板块。**

| 状态 | 值 | 视觉 | 含义 |
|---|---|---|---|
| 待办 | `pending` | 默认 | 尚未处理 |
| 已完成 | `done` | 🟢 绿 | 做完了 |
| 已忽略 | `ignored` | ⚪ 灰 | 决定不做，**不等于删除** |

**父节点完成条件（核心约束）**：

```
父节点可被标记为「已完成」  ⟺  它所有「参与判定」的直接子节点都处于 done 或 ignored
                              （没有参与判定的子节点时恒成立）
```

**判定域（v13 补齐，ADR-054）**：

| 直接子节点状态 | 是否参与父节点完成判定 |
|---|---|
| `deleted: true`（墓碑） | ❌ 不参与（视为不存在） |
| `archived: true`（已归档） | ❌ 不参与（**既不阻塞、也不满足**） |
| 其它 | ✅ 参与（必须为 `done` / `ignored`） |

> **为什么归档节点不参与**：4.7 的级联归档**不改变 `status`**。若归档的 `pending` 子项目参与判定，
> 父项目会被**永久阻塞**在未完成状态 —— 这是原设计中真实存在的死锁。

**适用范围**（Q38 明确：同一套理论适用于第二板块；Q54 明确：事件亦纳入）：

| 层级 | 父 → 子 | 是否适用 |
|---|---|---|
| 板块一 | 项目 → 子项目 | ✅ |
| 板块二 | **事件 → 顶层任务** | ✅ |
| 板块二 | 任务 → 子任务 | ✅ |
| 板块二 | 并列任务 → 其子任务 | ✅ |

> **因此完成条件是一条全系统统一规则**：
> **任意节点可被标记「已完成」 ⟺ 它所有参与判定的直接子节点都处于 `done` 或 `ignored`。**
> 该规则对 Project / Event / Task **完全一致** —— 四个实体中除 Inspiration 外，
> 全部采用同一套状态语义。

**反向传播（v13 新增，ADR-055）**：
> 父节点已 `done` 后，若其参与判定的子节点集合中**出现非终态**
> （新增一个 `pending` 子节点，或把某个终态改回 `pending`），
> 则**父节点自动退回 `pending`**，并沿祖先链继续向上传播。
>
> 方向不对称是**刻意**的：**自动「退回」允许**（让硬约束恒真），
> **自动「完成」仍然禁止**（ADR-007 不联动）。

**完成时刻**：标记为 `done` 时写入 `completed_at`（客户端时间戳）；退回 `pending` 或改 `ignored` 时置 `null`（ADR-058）。

**实现要点**：
1. 这是**硬约束**，UI 上表现为：条件未满足时"完成"操作被禁用，并提示原因
   （例如：`还有 2 个子项目未处理`）
2. 触发时机：**手动**。子节点全部完成时，**不自动**标记父节点完成（与 ADR-007 不联动一致）
3. `ignored` 是**终态**，但可撤销（改回 `pending`）
4. 参与「是否可完成」判断的只有**直接子级**，递归判断通过逐层约束自然成立
5. `Task` 的字段由 `done: boolean` 改为 `status`，与 `Project` 统一
6. `Event` 同样具备 `status` 与 `archived`（Q54 裁定），至此**全系统状态语义统一**
7. **判定域与反向传播必须实现在同一处**（`lib/core` 的状态机），UI 只消费结果，不得自行判断
8. **自动退回是唯一允许的自动状态变更**；除此之外，任何父节点状态变化都必须由用户触发

### 4.7 归档 ✅（v13 修正：双向级联 + 归档区）

**裁定**：`Project / Event / Task` 三个实体均支持归档。

| 项 | 规则 |
|---|---|
| 字段 | `archived: boolean` |
| 效果 | 从主视图隐藏，但数据完整保留、仍参与同步 |
| 可逆 | ✅ 可取消归档，且**取消时同样级联**（见下） |
| 与删除的区别 | 归档不置墓碑、不进回收站，也**不改变 `status`**；它触发的是**级联归档**而非级联删除 |
| 与"完成"的区别 | `done` 是结果状态，`archived` 是可见性开关，二者**正交** |
| 与完成判定的关系 | 归档节点**不参与**父节点完成判定（ADR-054，见 4.6） |
| 汇总入口 | 归档区「已归档」分区（4.10 / ADR-052） |

**连带规则（v13）**：
1. 归档一个节点时，其**全部后代一并归档**（级联归档：逻辑同 4.5，但不置墓碑、不改 `status`）
2. **取消归档时同样级联**：父节点取消归档 → 其后代一并取消归档（ADR-051，用户裁定）
   > 已知代价（接受）：若某子节点此前被**单独归档**，会被父节点的取消归档一并解除。
   > 采用单一规则换取零额外字段与可预期的行为；需要时用户可再次单独归档它。
3. **三个实体规则一致**：归档 `Task` 级联其子任务；归档 `Event` 级联其**整条任务线**
4. 归档项目下的灵感**保留原归属**，不解除分配
5. **归档项目不参与全局搜索**（Q50 裁定），入口在归档区（Q52）
6. 归档项目下的**灵感一并隐藏**；取消归档时恢复（Q53）；从归档区打开该项目时灵感也可见
7. 归档区只列出**归档根节点**（父节点未归档者）；被级联归档的后代不重复列出

> **设计理由**：`archived` 与 `status` 分开，是因为存在两种真实需求：
> 「做完并归档」(`done` + `archived`) 与「暂时不想看到」(`pending` + `archived`)。

> ⚠️ **措辞修正（v13）**：灵感**没有** `archived` 字段（见 4.2.1）。
> 原文「灵感合并后自动归档」是**口语化说法**，落地方式是
> `status = merged` + 归档区「已合并」分区（见 4.8 / ADR-038），**不新增字段**。

### 4.8 灵感合并方式 ✅

**裁定**：合并采用**上下分区的编辑器**，用户手动完成内容整合。**不是** git 式左右对比。

**交互流程**：
```
① 在灵感上点击「合并」按钮
② 进入合并编辑界面，屏幕纵向分区：
   ┌───────────────────────────────┐
   │  上区：项目的「实现」内容（可编辑）│  ← 主要工作区
   ├───────────────────────────────┤
   │  下区：灵感原文（供参考）         │  ← 对照来源
   └───────────────────────────────┘
③ 用户手动编辑上区，把灵感内容整合进去
④ 点击「保存」
⑤ 系统自动：写入 project.implementation
             该灵感置 status=merged + merged_into + merged_at
             （原灵感的归宿：归档区「已合并」分区）
```

| 项 | 规则 |
|---|---|
| 布局 | **上下分区**：上=项目实现（可编辑），下=灵感原文 |
| 是否自动追加 | ❌ **不自动**。合并结果完全由用户手动编辑决定 |
| 是否覆盖项目原文 | ❌ 由用户在上区编辑器中决定 |
| 保存后的灵感 | `status = merged` + `merged_into` + `merged_at`，从灵感列表消失（`deleted` 保持 `false`） |
| 可撤销 | ✅ `status` 可回退为 `pending`；**但撤销不回滚项目正文**（ADR-057，见下） |
| 数据冗余 | ❌ 项目里**不存**灵感副本，仅通过 `merged_into` 反向关联 |
| 可合并到哪一层 | **任意层级**的项目（含子项目）；`project_id` 与 `merged_into` 同时指向该项目 |
| 撤销入口 | 归档区「已合并」分区（4.10） |
| 同步代价 | 同时改 `inspirations.json` + `projects.json` → **必须**走事务提交（5.9） |

> **⚠️ 撤销合并的真实语义（ADR-057）**：
> 同一个项目可能先后吸收多条灵感，并在此期间被反复编辑。若撤销时把 `implementation`
> 回滚到"合并前"的版本，会把**后续所有编辑与其它灵感的成果一并抹掉**。
> 因此撤销 = **把灵感退回「未分配 `pending`」并放回灵感列表**，项目正文由用户自行处理
> （灵感原文完整保留，可复制回去）。

> **悬挂引用规则（ADR-056）**：
> - `merged_into` 指向**已删除的项目** → 仅作历史留痕，UI 显示「原合并目标已删除」；
>   撤销合并后 `project_id` 置 `null`（回到未分配）。
> - 项目被删除时，其下**已合并灵感的处置见 4.5**：回退为未分配 `pending`，不随级联删除消失。
> - 归档项目下的已合并灵感随项目隐藏；从归档区可查看并撤销。

> **架构含义**：这是**交互密集、逻辑极简**的功能。
> 数据层只需三个字段（`status` / `merged_into` / `merged_at`），
> 复杂度全部落在"上下分区编辑"这个 UI 上。
> 这正是 ADR-023（共享业务层、两套 UI 外壳）的典型受益点 ——
> 电脑端可让上区占更大比例以便长文编辑，手机端可把下区折叠成可展开的参考条。

### 4.9 任务节点呈现规则 ✅

**裁定**：子任务与其父节点**共用同一个节点框**；并列任务是**独立的节点框**。
**并列任务同样可以拥有自己的子任务。**

```
┌─────────────────────────────┐
│ ■ 标准任务 A                 │  ← 主任务与它的子任务同框
│   └ ☑ 子任务 A-1             │
│   └ ☑ 子任务 A-2             │
└─────────────────────────────┘
┌──────────────────────┐  ┌──────────────────────┐
│ ■ 并列任务 B          │  │ ■ 并列任务 C          │  ← 独立成框 = 分叉
│   └ ☑ 子任务 B-1      │  │   └ ☑ 子任务 C-1      │  ← 各自也可带子任务
└──────────────────────┘  └──────────────────────┘
```

| 类型 | 渲染 |
|---|---|
| `standard` | **独立节点框**；同一事件下的标准任务**沿主线纵向排列、用连线表示次序**（兄弟链，非嵌套） |
| `subtask` | 渲染在**父节点框内**，缩进列表（叶子，无子节点） |
| `parallel` | **独立节点框**，与兄弟**并列排布**，表达分叉；其子任务仍在**该框内** |

> **`standard` 与 `parallel` 的呈现差异（v13 明确）**：
> 两者都是独立框，区别在**排布方向与语义** ——
> `standard` 沿主线**串联**（纵向、有连线，表示"接着做这件事"）；
> `parallel` 与兄弟**并联**（横向并排、无连线，表示"两条都可走"）。
> 这消除了原文中"两者看起来都是框、差别不明"的歧义。

**关键规则**：
> `task_type` 是**渲染提示**（三类共用同一 schema），但**允许的父子组合受 4.4 的表约束**
> （ADR-053 修正 ADR-040）；越界数据按 `subtask` 渲染并记录日志，不崩溃。

> **这是纯 UI 层规则，不影响数据模型** —— 三类任务仍共用同一 schema，
> 树结构也不变（`parallel` 与 `subtask` 都是子节点，只是渲染方式不同）。
> 本裁定进一步确认 ADR-008 与 ADR-007 的合理性。

### 4.10 归档区（统一收纳区）✅（v13 新增，ADR-052）

**定位**：**所有「从主视图消失」的东西必须有唯一去处**，否则用户不知道去哪找、也没有后悔药。
归档区不是新实体，而是**视图聚合**，完全由既有字段（`archived` / `status` / `deleted`）推导。

| 分区 | 收录条件 | 可用操作 |
|---|---|---|
| **已归档** | `archived:true` 的 Project / Event / Task（**只列归档根**，父未归档者） | 取消归档（级联）、彻底删除 |
| **已丢弃** | 灵感的 `status = discarded` | 恢复为 `pending`、彻底删除 |
| **已合并** | 灵感的 `status = merged` | 撤销合并（ADR-057）、彻底删除 |
| **回收站** | 全部 `deleted:true` 的记录（含级联进来的后代；只列级联根） | 恢复、彻底删除 |
| 本地草稿（不同步） | `conflicts/*.json`（5.10）与残留 `*.tmp` | 查看、删除 |

> Q15 的「回收站」在此**并入归档区**：不再单独设一个回收站页面，
> 「合并后灵感」的后悔药由「已合并」分区承担。

**彻底删除（唯一不可恢复的路径）**：
```
在归档区选中 → 二次确认（显示影响范围）→ 墓碑骨架化
  · 置 deleted = true（防止离线端把数据推回，ADR-003 不变）
  · 清空业务字段（title / text / purpose / implementation / date / due_at …）
  · 仅保留 { id, deleted, purged_at } 作为「墓碑骨架」
  · 从归档区列表消失，App 内不再提供任何恢复入口
```

> **与 Q33「墓碑不清理」的调和**：墓碑对象**永不物理删除**（ADR-003 的安全底线），
> 但**内容可以被抹掉** —— 「彻底删除」抹的是**内容**，不是墓碑。
> 这样既满足「永久删除」的用户语义，又不会让离线端把已删数据复活。
> Q33 的结论由此**收窄为**：不做墓碑的物理清理。

**二次确认文案模板**：
`「彻底删除项目 A」将不可恢复地删除 3 个子项目、7 条灵感。此操作无法撤销。确认？`

### 4.11 层级、排序与移动规则 ✅（v13 新增，ADR-060）

**深度上限**：

| 结构 | 上限 | 计数基准 |
|---|---|---|
| 项目嵌套 | **3 层**（Q27） | 根项目 = 第 1 层 |
| 任务树 | **3 层**（不含 Event） | 标准任务 = 第 1 层；子任务 / 并列任务 = 第 2 层；并列任务的子任务 = 第 3 层 |

超出上限：UI 禁用创建入口；读取到越界数据时**照常显示但不允许继续加深**（不崩溃）。

**排序**：
- 同一父节点下的兄弟用 `order` 整数，间隔 1000（4.0）
- 拖拽插入取相邻两值的**中位数**
- **间隙耗尽**（相邻差值 < 2）时，**对该父节点下的全部子节点整体重编号**为 1000, 2000, 3000…
  （一次文档级写入，随普通同步推送，无需专门协议）
- `order` 只表达**次序**，不构成依赖（A3 不联动仍然有效）

**移动校验（必须拦截）**：

| 规则 | 说明 |
|---|---|
| 禁止移入自身或自身后代 | 会造环；拖拽时就把非法目标置灰 |
| 不得突破层级上限 | 见上表 |
| 跨父移动允许 | Q36：子项目可跨父项目移动（受前两条约束） |
| 跨事件移动任务 | 允许（改 `event_id`）；**移动后 `parent_task_id` 必须为 `null` 或指向同一事件内的父节点**，禁止跨事件父子 |
| 类型不因移动而改变 | `task_type` 是渲染提示（4.9），移动不改写它 |
| 移动是文档级变更 | 只改 `projects.json` 或 `tasks.json`（单文档，无需事务） |

### 4.12 灵感列表规则 ✅（v13 新增，ADR-065）

| 项 | 裁定 |
|---|---|
| 排序 | `created_at` **倒序**（最新在上）；灵感不设 `order` 字段（保持 4.2.1） |
| 已分配但未合并（`pending` + `project_id ≠ null`） | **同时出现**在灵感列表（带项目标签）与该项目下。理由：分配 ≠ 处理完毕，灵感列表是"待处理收件箱" |
| 未分配 | 留在灵感列表（Q34 默认未分配） |
| `merged` | 从灵感列表消失（被吸收）；入口在归档区「已合并」 |
| `discarded` | 从灵感列表消失；入口在归档区「已丢弃」，可恢复为 `pending` |
| 归档项目下的灵感 | 随项目隐藏；从归档区打开该项目时可见 |
| 搜索范围 | 只搜 `pending` 的灵感；`merged` / `discarded` / 归档 / 墓碑**一律不参与**（与 Q50 口径一致） |

## 5. 同步机制设计 ✅

### 5.1 客户端本地辅助结构（已按 L1 简化）

| 结构 | 作用 | 状态 |
|---|---|---|
| `dirty` 标记 | 标记哪个文档被改过，需要推送 | ✅ 需要 |
| `doc_version` | 每份文档的版本号 —— **存于本地实体文件的外层**（与云端逐字节同构），不再单独存放（见《数据契约》§2） | ✅ 需要 |
| `sync_state.json` | 同步元数据：`schemaVersion` / `accountId` / `firstSyncDone` / `lastSyncAt`（见 5.10） | ✅ 需要（本地） |
| **`pending_tx`（待完成事务）** | 跨文档操作的**重放凭据**（见 5.9 / ADR-050）。取代通用 outbox —— **只记"尚未提交的事务"，不记逐条变更** | ✅ **需要** |
| `ui_prefs.json` | 折叠状态等视图偏好 | ✅ 需要（本地，**不参与同步**，ADR-059） |
| `outbox`（逐条变更队列） | 逐条变更上报 | ❌ 不需要（L1 整文档推送） |
| `cursor`（seq 游标） | 增量拉取位置 | ❌ 不需要（靠 version 比对） |
| `history` | 被覆盖的旧值 | ❌ 不需要（单人使用不做字段级合并，见 5.4 / 5.6） |

> 同步机制已由 5.6 的「文档版本号模型」统一定义，5.2 保留原始设计作为演进记录。
> **注意**：5.1 表中 `outbox` 与 `pending_tx` 的区别正是它"不需要"的原因 ——
> outbox 记录**每一条字段级变更**，`pending_tx` 只记录**一个跨文档事务边界**（最多几 KB）。

### 5.2 原始增量设计（历史记录，已不采用）

**Push**：读 outbox → 逐条上报（条件 `version` 匹配）→ 成功则 `version+1` 并清队列。

**Pull**：请求 `seq > cursor` 的记录 → 按 seq 升序写入本地 → 更新 cursor。

> 该设计适用于「多人协作 / 十万条级」场景。本项目已确认单人 + 数千条，故降级为文档级同步。

### 5.3 实现档位裁定 ✅

**规模已确认**：单人使用，数据量数千条以内。

| 档位 | 方案 | 结论 |
|---|---|---|
| **L1 文档级同步** | 云端按实体类型分文档存 JSON，读时整体覆盖 | ✅ **采用** |
| L2 增量同步 | change log + seq 游标 | ⬜ 暂不采用，但接口需预留 |

**L1 的具体形态（四文档分区）**：

```
用户数据
├── projects.json      项目树（含嵌套子项目）
├── inspirations.json  灵感列表
├── events.json        事件列表
└── tasks.json         全部任务（含任务树）
```

每份文档的云端结构：
```json
{
  "version": 42,
  "updated_at": 1735000000000,
  "payload": {
    "items": [ /* 该实体类型的全部记录，含 deleted:true 的墓碑 */ ]
  }
}
```

- **墓碑保留完整对象**，而非只保留 ID。这样删除/合并的操作可撤销，无需额外的 history 表
- `inspirations.json` 中被**合并**的灵感以 **`status = "merged"` + `merged_into` + `merged_at`**
  留在 `items` 里（`deleted` 保持 `false`），既不出现在灵感列表（UI 按 status 过滤），
  又完整保留内容（可从归档区「已合并」撤销）
  > ⚠️ **v13 修正**：此前本节写作「以 `deleted:true` + `merged_into` 留在 items 里」，与 4.2 / ADR-038
  > 冲突。**合并不使用 `deleted` 表达** —— `deleted` 只表示「被删除」（进回收站）。
- 墓碑的清理：**不做物理清理**（Q33）。内容的抹除只通过归档区的「彻底删除」（墓碑骨架化，见 4.10 / ADR-052）发生

- 每个文档独立带 `version` + `updated_at` + `last_tx_id`
- 改动某个项目 → 只推送 `projects.json`，其余三份不动
- **分区而非单一大包**：既保留 L1 的实现简单性，又把冲突范围限制在单个实体类型内
- **任务全部放在一份 `tasks.json` 里**（不按事件拆分），理由是跨事件移动任务、以及「全部任务」视图都需要全量数据；数千条规模下拆分的收益小于成本

**云端（CloudBase）落地形态**：文档型数据库的单个集合 `documents`，每条记录即一份文档：

```json
{
  "_id": "projects.json",
  "accountId": "a-xxxx",
  "version": 42,
  "updated_at": 1735000000000,
  "last_tx_id": "uuid",
  "payload": { "items": [ /* 不透明 JSON，云函数不解析 */ ] }
}
```
> 集合按 `accountId` 分区；`payload` 对云函数**完全不透明**（见 2.2 的新增约束）。

> **量级评估**：数千条记录 → JSON 约 0.5～2 MB，日常增量推送在 4G 网络下可接受。
> **升级触发条件**：任一实体超过约 5000 条，或单文档超过 5 MB，即迁移到 L2。
> 迁移成本可控，因为 L1↔L2 只影响传输层，不影响数据模型。

### 5.3.1 L1 下的冲突处理（已简化）

由于已确认为**单人使用**：

- 双端同时编辑**同一条记录**的概率极低
- 冲突策略仍采用 LWW，但**无需复杂的字段级合并**
- 唯一需要处理的场景：一端改了 A 项目、另一端改了 B 项目 → **天然无冲突**（不同记录）

### 5.4 冲突策略（文档级 LWW + 人工选择）✅（v13 重写）

- 默认：**文档级 Last-Write-Wins**，以服务端 `version` / `updated_at` 为准（5.6）
- 单人场景下唯一可能的冲突：两端几乎同时保存**同一份文档**
- 处理：**不自动合并**，提示用户选择「以云端为准 / 以本地为准」（流程见 5.10）
- ❌ **不做**字段级合并、❌ **不做** CRDT、❌ **不做** `history` 表

> ⚠️ **v13 修正**：本节此前写作「字段级 LWW + 旧值写入 `history` + 树移动需专门设计」，
> 与 5.6 的简化结论以及 5.1 的"不需要 history"直接冲突，已按 5.6 统一。
>
> **结构性冲突（原「移动节点」风险）如何消解**：
> ① 任务线是**纯树**且无依赖边（4.4 / A1）；
> ② 移动受 4.11 的**环路与层级校验**约束，客户端在写入前就拦截非法移动；
> ③ 因此冲突退化为「整份 `tasks.json` 谁更新」的**文档级冲突**，与其它文档同构，
> **不需要专门的冲突设计**。

### 5.5 同步触发时机 ✅（v13 修正）

| 平台 | 触发手段 | 可靠性 |
|---|---|---|
| 双端 | App 启动 / 切回前台 | 高 |
| 双端 | 手动刷新 / 网络恢复监听 | 高 |
| Android | WorkManager 定期任务（≥15min） | 中 |
| iOS | 后台任务 | **不可靠**（第一版不做 iOS，见 ADR-061） |
| Windows | 开机自启 + 托盘常驻 + **5 分钟轮询**（Q45） | 高 |
| ~~双端~~ | ~~推送唤醒（APNs/FCM）~~ | ⚠️ **v13 移除**：FCM 在中国大陆不可用；CloudBase 不提供推送通道；且推送唤醒只优化"多久发现变更"，不承担正确性（ADR-062） |

**每次同步的固定顺序**：先补发 `pending_tx` → 再 Push dirty → 最后 Pull。详见 5.10。

**流量约束**：轮询**不得**每次下载整包 payload —— 先取版本号元数据，只在版本变化时才拉取（见 5.6 的 `getVersions`）。

### 5.6 同步的核心简化：版本号挂在**文档**上，不挂在记录上 ✅

这是本项目最重要的架构决策之一。

传统做法是「每条记录一个 version」，那需要逐条比对、逐条冲突检测。但我们已确认：

- 单人使用 → 不存在多人并发
- 数据量数千条 → 整包体积可接受
- 四文档分区 → 冲突范围被限制在实体类型内

因此：

```
每个文档独立持有：
  version     整数，每次修改 +1
  updated_at  服务端时间戳
  payload     该实体类型的全量 JSON
```

**Push**：`callFunction('commitTx')`，请求体带 `base_version`（见 5.9）
 → 云函数比对 `base_version == 当前 version`
 → 相等则接受并 `version+1`、写入 `last_tx_id`；不等则返回冲突（409 语义）

**Pull（两段式，v13 修正）**：
```
① callFunction('getVersions')  → { "projects.json": 43, "tasks.json": 12, ... }
                                  （只返回版本号与 updated_at，几百字节）
② 仅当某文档 version > 本地 doc_version 时，才 getDoc(name) 拉取 payload 整体替换
```
> **为什么必须两段式**：Q45 要求电脑端每 5 分钟轮询一次，而整包是 0.5~2 MB。
> 每次全量下载会造成每天数百 MB 的无谓流量。**轮询只能读元数据。**

**冲突处理简化到极致**：
- 单人使用下，冲突基本只可能因为「两端几乎同时保存」
- 处理方式：提示「云端已有更新，请选择保留哪一份 / 重新加载」，并**先落地本地草稿**（5.10）
- **不需要字段级合并，不需要 CRDT，不需要 history 表**

### 5.6.1 云函数的三个入口（`SyncBackend` 的实现面）✅（v13 新增）

| 云函数 | 入参 | 出参 | 职责 |
|---|---|---|---|
| `commitTx` | `{ tx_id, docs:[{name, base_version, payload}] }` | `{ ok, versions }` / `{ conflict, remote_versions }` | **唯一写入口**：事务内 CAS + 写入 + `version+1` + `last_tx_id` |
| `getVersions` | `{}` | `{ name: {version, updated_at} }` | 只读元数据，供轮询探测 |
| `getDoc` | `{ name }` | `{ version, updated_at, payload }` | 读取整包 payload |

> 账号相关云函数（`registerAccount` / `pair` / `issueTicket`）见 7.2。
> **云函数只认识 `version` / `updated_at` / `last_tx_id` 三个字段，`payload` 对它不透明。**

### 5.7 客户端本地存储：不要引入数据库 ✅

**关键洞察**：既然传输层是「四份 JSON 文档」，本地存储就应该**同构**。

| 方案 | 评价 |
|---|---|
| Isar / ObjectBox / SQLite | ❌ **过度设计**。数千条数据不需要索引与查询引擎 |
| Drift / sqflite | ❌ 引入 schema、迁移、ORM 三份复杂度 |
| **JSON 文件 + 内存态** | ✅ **采用** |

**本地架构**：
```
App 启动
  └─ 读取 4 份 JSON 文件 + sync_state.json + ui_prefs.json
      └─ 若存在残留 pending_tx.json → 先补发事务（5.9）
          └─ 反序列化为内存中的单一数据源对象（Single Source of Truth）
              └─ 所有 UI 读写内存对象
                  └─ 内存对象变更 → 防抖 1～2 秒 → 序列化落盘
                      └─ 同时标记该文档为 dirty
                          └─ 触发同步 → 推送 dirty 文档
```

**落盘必须原子（v13 新增）**：
1. 写 `xxx.json.tmp` → `fsync` → `rename` 覆盖 `xxx.json`（同目录 rename 是原子操作）
2. 启动时若发现残留 `.tmp`，**直接忽略并删除**（说明上次写在中间崩了，原文件仍完整）
3. **关键操作立即落盘，不等防抖**：合并灵感、删除、归档/取消归档、批量移动、彻底删除
   —— 这些操作"用户以为已经生效"，移动端进程被系统杀掉时不能丢
4. 落盘失败的兜底：保留 `.tmp` 并在下次启动时提示（不静默丢弃）

> **本地文件清单（v13）**：`projects.json` / `inspirations.json` / `events.json` / `tasks.json`
> （**参与同步**）；`sync_state.json` / `pending_tx.json` / `ui_prefs.json` / `conflicts/*` / `capture_inbox.*`
> （**不参与同步**）。

**收益**：
1. 本地模型与云端模型**完全一致**，不需要任何映射层
2. 无需 schema 迁移（加字段就是 JSON 多一个 key，老数据缺失即为默认值）
3. 无需 ORM、无需查询构建器，代码量大幅下降
4. 树形结构在内存里就是嵌套对象，天然契合

**代价**（可接受）：
- 全量落盘：数千条 JSON 序列化耗时在几十毫秒级
- 无 SQL 查询：改为内存中 filter/sort，数千条无性能问题

> **升级触发条件**：若数据超过约 2 万条导致启动加载变慢，再引入 SQLite 做冷数据分页。
> 届时内存对象仍是唯一真源，数据库只是缓存层，架构不需推翻。

### 5.8 电脑端的角色定位 ✅

在 C2（电脑不保证开机）前提下，电脑端是**完全对等的客户端**，无任何特殊职责：

| 职责 | 手机端 | 电脑端 |
|---|---|---|
| 读写本地数据 | ✅ | ✅ |
| 推送变更到云端 | ✅ | ✅ |
| 从云端拉取变更 | ✅ | ✅ |
| 作为中转/服务端 | ❌ | ❌ **绝不** |
| 开机自启 + 5 分钟轮询 | — | ✅ 额外增强（Q45） |
| 后台定期同步 | Android WorkManager 可行 / iOS 不可靠 | ✅ 可行（托盘常驻） |
| 承担跨文档事务 | 否 | 否（**由 CloudBase 云函数承担**，ADR-064） |

### 5.9 跨文档变更：待完成事务 + 云函数原子提交 ✅（v13 新增，ADR-050）

**问题**：一次业务操作可能同时改多份文档，而 L1 的分区是按**实体类型**切开的：

| 业务操作 | 涉及文档 |
|---|---|
| 灵感合并 | `inspirations.json` + `projects.json` |
| 删除项目（级联） | `projects.json` + `inspirations.json` |
| 归档 / 取消归档（级联） | 归档 **Event** → `events.json` + `tasks.json`（两份，需事务）；归档 **Project** → 仅 `projects.json`（其下灵感只做派生隐藏，**不改字段**）；归档 **Task** → 仅 `tasks.json` |
| 跨事件移动任务 | `tasks.json`（单文档，无风险） |

两次写之间断网，云端会停在**半成品状态**，而 5.4 的冲突策略里没有任何修复手段
（原文档 §4.5 写「一次同步即可」，这是不成立的假设）。

**裁定**：**云端原子 + 客户端可重放**，两层保障。

**(1) 云端：云函数内的事务提交**
```
客户端 → callFunction('commitTx', { tx_id, docs: [
    { name: "projects.json",     base_version: 12, payload: {...} },
    { name: "inspirations.json", base_version: 9,  payload: {...} }
]})
  └─ 云函数（Node SDK，ADR-064）：
       db.runTransaction(tx => {
         ① 逐个读取当前 version，校验 == base_version（任一不等 → 抛冲突）
         ② 全部通过后，才逐个写入 payload + version+1 + updated_at（服务端时间）
         ③ 每个文档写入 last_tx_id = tx_id
       })
  └─ 全成或全败（CloudBase 事务保证 ACID；上限 100 次操作 / 30 秒）
```
> 单文档变更**同样走 `commitTx`**（`docs` 长度为 1），保证只有一条写入路径。

**(2) 幂等**：响应丢失后客户端重试时，云函数先判
`当前 version != base_version` **且** `last_tx_id == tx_id` → 判定「这次事务其实已成功」，
直接返回 `ok`（不重复 +1、不报冲突）。

**(3) 客户端：待完成事务标记（对应用户裁定的「待完成事务」）**
```json
// pending_tx.json（本地；不参与同步、不参与版本）
{
  "tx_id": "uuid",
  "created_at": 1735000000000,
  "docs": [ { "name": "projects.json", "base_version": 12 } ],
  "retry": 0
}
```
- 任意跨文档操作在**改内存 → 落盘 dirty** 的同一时刻写入 `pending_tx.json`
  （payload 仍在内存与 4 份文档里，不重复存储，避免体积翻倍）
- 提交成功后**立即删除**；失败则下次同步**优先补发该事务**，再处理普通 dirty 文档
- 启动时若发现残留 `pending_tx`，**先补发再拉取**，避免把半成品状态当成基线
- `retry >= 3` 仍失败 → 在 UI 上暴露「有 1 个未完成事务」，并提供手动重试

> ⚠️ **禁止**：任何跨文档操作都不允许退化为「两次独立 PUT」。
> 这一条必须有**单元测试守护**（`test/sync/` 中检查跨文档用例只调用一次 `commitTx`）。

### 5.10 冷启动、首次同步与冲突恢复 ✅（v13 新增，ADR-066）

**首次启动判定表**（依赖 `sync_state.json` 是否存在 + 本地是否有数据）：

| 本地 | 云端 | 行为 |
|---|---|---|
| 空 | 空 | 建立基线，version 从 0 开始 |
| 空 | 有文档 | **直接拉取覆盖**（云端是唯一真相源） |
| 有数据 | 空（全新账号） | 全部标记 dirty → 首次推送 |
| 有数据 | 有文档，且本地**从未同步过**（无 `doc_version`） | **不自动覆盖**：弹窗二选一（默认建议「以云端为准」，另一项为「以本地为准并覆盖云端」） |
| 有数据 | 有文档，本地有 `doc_version` | 正常增量流程（见下） |

**每次同步的固定顺序**：
```
① 若有残留 pending_tx → 先补发（失败即终止本轮，不做后续步骤）
② 对每个 dirty 文档 → Push（带 base_version）
      ├─ 成功 → 清 dirty、更新本地 doc_version
      └─ 冲突 → 进入冲突流程，本轮不再推送该文档
③ Pull：先 getVersions 探测 → 仅对 version 更大的文档 getDoc 并整体替换
④ 落盘 sync_state.json
```
> **先 Push 后 Pull** 的理由：避免 Pull 把本地尚未推送的改动直接覆盖掉。

**冲突流程**：
1. 提示：「云端已有更新（v43），本地有未推送的修改。保留哪一份？」
2. 选「以云端为准」→ 本地未推送内容**先写入本地草稿**
   `conflicts/conflict_<doc>_<timestamp>.json`（不参与同步、不进版本），**再**整体替换本地
3. 选「以本地为准」→ 用云端最新 `version` 作为新的 `base_version` 重推（等于放弃云端那一版）
4. 草稿在归档区「本地草稿」分区可见，可查看与删除

> **不做**：字段级合并、CRDT、history 表、自动合并（5.6 的裁定保持有效）。

## 6. 技术栈裁定 ✅

| 层 | 选型 | 理由 |
|---|---|---|
| **客户端框架** | **Flutter**（一套代码，手机 + 电脑） | 同步逻辑、数据模型、业务规则 **100% 复用**；单人开发工作量最低 |
| **本地持久化** | JSON 文件 + 内存单一数据源 | 与云端同构，见 5.7 |
| **状态管理** | Riverpod / Provider（Flutter 生态） | 单一数据源天然适配响应式状态 |
| **UI 适配** | 响应式布局（手机竖屏 / 电脑宽屏） | 一套 widget 适配两种形态 |
| **云端** | **腾讯云开发 CloudBase**（见 6.1） | 只做「存 4 个 JSON 文档 + 提供事务化 CAS」这两件事 |
| **服务端逻辑** | CloudBase 云函数（Node.js，仅 6 个函数） | 版本 CAS、跨文档事务、签发登录票；**不自建进程**（C1） |
| **对象存储** | ❌ **不需要**（已确认纯文本） | 省去预签名直传、上传重试等整块复杂度 |
| **账号体系** | ❌ **不做多账号**（已确认单人使用），但需**可迁移的身份根** | 恢复码 + 配对码 + 自定义登录票（见 7.2） |

### 6.1 云端选型 ✅（v13 变更：LeanCloud 国内版 → 腾讯云开发 CloudBase）

**已定：腾讯云开发 CloudBase（云函数 + 文档型数据库）**

> ⚠️ **变更原因（ADR-048）**：LeanCloud 已发布[停服公告](https://docs.leancloud.cn/sdk/announcements/sunset-announcement/) ——
> **2026-01-12 起停止新用户注册与新应用创建，2027-01-12 全面停止服务**，届期平台内数据将被销毁。
> 原 ADR-018 的方案在 2027-01 之后不可用。
> 同时原文档「免备案域名」的选型理由**并不成立**：LeanCloud 官方
> [域名常见问题](https://docs.leancloud.cn/sdk/domain/faq/)写明「开发版应用无法在 LeanCloud 备案，
> 需自行购买独立 IP 或升级商用版」，且中国版自 2019 年起强制绑定自有域名。

| 为什么选 CloudBase | 说明 |
|---|---|
| 国内直连 | 上海 / 广州地域，无需代理，无 Google 依赖 |
| **官方 Flutter SDK** | [`cloudbase_flutter`](https://docs.cloudbase.net/api-reference/flutter)（1.2.x），覆盖 Android / iOS / Windows / macOS / Linux，与 ADR-011 技术栈直接匹配 |
| **Serverless 云函数 + 数据库事务** | 事务仅在服务端 node-sdk 可用（[事务文档](https://docs.cloudbase.net/database/transaction)），正好满足 ADR-050 的跨文档原子性与 ADR-064 的单一写入口 |
| 官方迁移路径 | 腾讯云提供[ LeanCloud 迁移指南](https://docs.cloudbase.net/run/migration/leancloud) |
| 认证能力 | 匿名 / 自定义登录（custom ticket）/ 密码 / OTP，支撑 ADR-049 的配对码方案 |
| 免费额度 | 开发测试期数据量（4 份 JSON、数千条）远低于计费门槛；**开通前须核对最新价格文档**（`cloud.tencent.com/document/product/876/127357`） |

**必须登记的两个风险**：
1. **默认域名限制**：CloudBase 默认域名官方定位为「开发测试」用途，存在访问频率限制与稳定性提示
   （见 [HTTP 网关 · 默认域名](https://docs.cloudbase.net/service/introduce)）。App 的**接口访问**可用，
   但若遇到限频，需绑定**已备案的自定义域名** —— 届时应预留域名与备案成本。
2. **平台依赖已被验证过两次**：这是第二次因服务商终止而更换云端。因此
   `SyncBackend` 抽象必须**真实落地**，不得让 CloudBase SDK 类型泄漏到业务层 ——
   业务层只允许出现自有的 `DocName` / `DocSnapshot` / `CommitResult` 等类型（ADR-019）。

> **保留退出路径**：CloudBase 只是 `SyncBackend` 的一个实现。
> 若额度或条款变化，替换为 Supabase / Bmob / 自建 Serverless 只需新增一个实现类 + 一组云函数，
> 业务代码不动。**注**：C1 允许部署 Serverless 云函数（不属于「自建服务器」），见 ADR-064。

### 6.2 客户端分层 ✅

由于已确认**双端有侧重**（3.1.1），客户端不是"一套 UI 跑两端"，而是**三种分层**：

```
┌──────────────────────────────────────────────┐
│  UI 层                                        │
│   ├── 共享组件（树视图、列表项、编辑表单）        │
│   ├── 手机外壳（Tab 导航，速记优先）             │
│   └── 电脑外壳（侧栏 + 多栏，编辑优先）          │
├──────────────────────────────────────────────┤
│  业务逻辑层  ← ★ 100% 共享，无平台判断          │
│   项目管理 / 灵感合并 / 任务树操作 / 级联删除     │
├──────────────────────────────────────────────┤
│  数据层  ← ★ 100% 共享                        │
│   内存单一数据源 / JSON 序列化 / 树操作          │
├──────────────────────────────────────────────┤
│  同步层  ← ★ 100% 共享（SyncBackend 接口）     │
├──────────────────────────────────────────────┤
│  平台适配层  ← 唯一需要分平台的部分              │
│   文件路径 / 钥匙串 / 小组件 / 开机自启 / 后台任务│
└──────────────────────────────────────────────┘
```

**核心原则**：
> **平台差异只允许出现在 UI 层和平台适配层。业务逻辑与数据层不得出现 `Platform.isAndroid` 这类判断。**

这是"一套代码吃双端"能成立的关键 —— 一旦业务逻辑开始分平台，
共享代码的收益就会被侵蚀，最后退化成"两套 App 塞在一个仓库里"。

**双端取舍对照**：

| 能力 | 手机外壳 | 电脑外壳 | 共享层 |
|---|---|---|---|
| 灵感速记 | 首屏按钮 + 系统级入口 | 应用内快捷输入 | ✅ 同一套写入逻辑 |
| 项目编辑 | 简版表单 | 全功能表单 + 长文本 | ✅ |
| 任务树 | 折叠列表 + 勾选 | 拖拽 + 批量操作 | ✅ 同一棵树模型 |
| 全部功能可达 | ✅ 可进入 | ✅ 可进入 | — |

### 6.3 系统级灵感入口 ✅

已确认需要系统级入口。**平台可行性已评估，详见 8.2**。

**难点**：
> 小组件 / 通知栏按钮运行在**原生进程**中，不是 Dart 进程。
> 它无法直接操作内存中的单一数据源。

**解决方向**：

```
用户从小组件/通知栏输入
  └─ 原生层写入一个「待处理灵感」文件（append-only）
      └─ 下次主 App 启动或恢复前台
          └─ 读取该文件 → 合并进内存数据源 → 标记 inspirations 文档 dirty
              └─ 正常同步流程
```

| 平台 | 可行做法 | 限制 |
|---|---|---|
| **Android** | 桌面小组件（**点击后弹出对话框式 Activity 输入**）+ 常驻通知按钮 | ⚠️ `RemoteViews` **不支持 `EditText`**，小部件内无法直接输入 |
| **iOS** | 点击小组件跳转到灵感输入页 | ⚠️ 小组件不能接收文字输入 |
| **Windows** | 托盘图标 + 全局快捷键 | ✅ 体验最好，无系统限制 |
| ~~小米超级岛~~ | **已排除** | 仅 OS3 支持，且形态不匹配（详见 8.2） |

**架构含义**：
1. 需要一个 `CaptureInbox` 概念 —— 原生层与服务层之间的**单向投递通道**
2. 它是一个**极简的本地文件**，不参与同步，不参与版本控制
3. 主 App 消费后即清空，避免重复导入
4. 导入的灵感与手动创建的灵感**完全同构**，不引入新的实体类型
5. **必须是幂等的（v13 新增）**：每条 inbox 记录带 `capture_id`（UUID）+ `captured_at`；
   导入流程为「读入内存 → 按 `capture_id` 去重 → 原子重命名 inbox 文件为 `.consumed`
   → 写入内存数据源 → 删除 `.consumed`」。任何一步崩溃后重放都**不会产生重复灵感**。
6. **风险提示**：inbox 只在本机、不参与同步。若用户从小组件速记后**始终不打开 App**
   （或直接卸载），该条灵感只存在于本机 —— 这是"原生进程无法访问 Dart 内存态"的必然代价，
   需在小组件交互文案中提示「打开 App 后才会同步」。

> **优先级建议**：先把 App 内的灵感记录做扎实，系统级入口作为第二阶段增强。
> 它涉及两套原生代码（Android / Windows；iOS 不在第一版范围，见 ADR-061），
> 是双端项目里最容易拖慢进度的部分。

## 7. 安全与凭证设计 ✅

**前提**：已确认单人使用、**不做多账号体系**（ADR-010）。但**这不等于不需要身份** ——
两端必须能认出「这是同一个人的数据」，且这个身份必须**可迁移**（换机、重装）。
这是本项目最容易被忽略、后果最严重的环节。

### 7.1 核心风险

| 风险 | 说明 |
|---|---|
| 密钥可被提取 | 打包进 App 的任何密钥，都能被反编译/抓包获取。**不能把它当作安全边界** |
| 全量数据暴露 | 4 个 JSON 文档 = 用户的全部生活记录，一旦泄露是完整隐私 |
| 误配 ACL | 若为图省事关掉权限校验，任何人都能读写你的数据 |
| **身份不可迁移（v13 新增）** | 若身份只存在于本机（例如匿名账号），**卸载重装 / 换机 = 数据永久失联** |
| **两端各拿一个身份（v13 新增）** | 两端若各自注册，会看到两份互不相干的数据，同步可能永远不生效 |

### 7.2 采用方案：恢复码 + 配对码 + 自定义登录票 ✅（v13 重写，ADR-049）

**原方案的缺口**：此前写作「App 首次启动自动创建匿名账号」。但匿名账号是**每台设备各自创建**的 ——
手机与电脑会拿到两个不同账号、看到两份数据；且匿名账号**没有可迁移凭证**。

**裁定**：单人项目不引入"账号体系"（无注册页、无密码找回、无多租户），
但必须有**一个可迁移的身份根**：

```
【首端 · 初始化】
  ① 首次启动 → **客户端**生成 24 字符恢复码（Base32 字母表，剔除易混字符 0/O/1/I）
  ② 云函数 registerAccount(recoveryCode, deviceId, deviceName)
       → **服务端**生成 accountId，只存 sha256(salt + 恢复码)，并登记本设备
       （accountId 由服务端生成，避免客户端抢注）
  ③ 云函数签发 custom ticket（**uid 必须等于 accountId**）→ SDK 自定义登录 → 会话存系统钥匙串
  ④ UI **强制**引导用户抄写 / 离线保存恢复码（不落明文、不入日志）

【次端 · 配对】
  首端「添加设备」→ 云函数生成 6 位一次性配对码（TTL 5 分钟、单次有效）
  次端输入配对码 → 云函数校验 → 签发 custom ticket → 两端同一 accountId

【换机 · 恢复】
  输入恢复码 → 云函数校验哈希 → 重新签发 ticket
  恢复码可在设置中「重新生成」（旧码立即失效）
```

| 要点 | 规则 |
|---|---|
| 会话凭证 | custom ticket 换取的会话存 **Android Keystore / Windows 凭据管理器 / iOS Keychain**，不放明文文件 |
| 不硬编码 | 客户端只内置 **envId + Publishable Key**（仅用于公开资源访问），**不含任何服务端密钥或 Secret** |
| **客户端不直连数据库** | 所有读写经云函数（唯一入口），隔离与版本校验集中在服务端（ADR-064） |
| 数据隔离 | `documents` 集合按 `accountId` 分区；云函数**强制**使用会话中的 `accountId`，**不接受客户端传入** |
| 多设备 | 不设硬上限；`devices` 集合记录 `deviceId` + 最后活跃时间，可单独吊销某一台 |
| 恢复码丢失 | 数据无法通过任何合法路径取回 —— UI 必须在此处做**最高级别**提示（"这是唯一凭证"） |
| 反模式 | ❌ 客户端直连数据库并依赖安全规则 ❌ 把 accountId 当参数传给云函数 ❌ 把恢复码存进普通配置文件 |

### 7.3 数据加密（可选增强，非基线）

| 层级 | 措施 | 备注 |
|---|---|---|
| 传输 | HTTPS | CloudBase SDK 默认 |
| 落库 | 云端加密 | 由服务商提供 |
| **端到端** | 本地派生密钥加密 JSON 后再上传 | ⚠️ 更强隐私，但密钥丢失 = 数据永久无法恢复 |

> **建议**：第一版不做 E2EE。个人工具的威胁模型主要是「云端被拖库」和「token 泄露」，
> 前者由服务商负责，后者由 ACL 限制。E2EE 的密钥管理成本（尤其是换机、忘密码）对单人项目偏高。

### 7.4 必须避免的反模式 ❌

- ❌ 把 App Secret / 服务端密钥写死在代码里并关闭权限校验
- ❌ 用「固定用户ID + 公开读」图方便
- ❌ 把数据同步到公共可读的集合
- ❌ 只依赖「别人不知道我的 envId」这种隐晦式安全
- ❌ 让客户端直连数据库并依赖安全规则兜底（v13 新增，ADR-064）
- ❌ 把 `accountId` 作为云函数入参并信任它（V13 新增）

## 8. 跨平台接入评估 ✅

### 8.1 电脑端技术栈：已裁定 —— **统一使用 Flutter** ✅

> **决策**：双端均为 Flutter。WPF 方案**评估后放弃**，理由是工作量增加约 60%
> 且引入「两套实现静默分叉」的风险，收益不足以抵消。

| 项 | 裁定结果 |
|---|---|
| 客户端技术栈 | **Flutter 单栈**，手机 + 电脑 |
| 数据层 / 业务层 / 同步层 | **单一实现，100% 共享** |
| 平台差异范围 | 仅限 UI 层与平台适配层（ADR-024 强化） |
| 跨端 JSON 契约测试 | 降级为**推荐**（单实现下不再是必须，但仍建议保留序列化回归测试；ADR-028 已被取代） |
| 电脑端形态 | Flutter Desktop（Windows 优先） |
| **交付平台范围（v13 新增）** | **第一版 = Android（手机端）+ Windows（电脑端）**。**iOS / macOS / Linux 不排期**（ADR-061：无 Mac 构建机与 Apple 开发者账号，且非首要场景） |

**放弃 WPF 所规避的风险**（留档备查）：

| 风险 | 说明 |
|---|---|
| 工作量 | 数据层 + 业务层 + 同步层需重写，约 +60% |
| 静默损坏 | 两套实现对 JSON 理解不一致时**不报错**，只损坏数据 |
| 平台锁定 | WPF 为 Windows-only，将来上 Mac/Linux 需推翻重写 |
| 冲突逻辑分裂 | 409 处理、操作重放等最容易分叉的部分被复制两遍 |

> 且不具备 WPF 那样的原生 Windows 观感。若将来对此不满，
> 可考虑 Avalonia 作为局部替代，但**不应拆分同步层**。

### 8.2 小米 15 Pro 平台能力评估 ✅（v13：仅 Android 在范围内，见 ADR-061）

依据[小米澎湃OS开发者平台 · 小米超级岛开发指南](https://dev.mi.com/xiaomihyperos/documentation/detail?pId=2131)。

| 能力 | 可行性 | 关键限制 |
|---|---|---|
| **桌面小组件** | ✅ 可行 | Android `RemoteViews` **不支持 `EditText`**，无法在小部件内直接输入。需做成「点击小部件 → 弹出对话框式 Activity 输入」 |
| **通知栏快捷入口** | ✅ 可行 | 常驻通知 + 按钮 → 进入输入页 |
| **小米超级岛** | ⚠️ 不建议 | 见下 |

**小米超级岛的关键事实**：

| 事实 | 说明 |
|---|---|
| 正式名称 | 小米超级岛（非"灵动岛"） |
| 接入方式 | 通知附加 `miui.focus.param` 扩展参数，或走 MIPUSH |
| **版本门槛** | **仅 OS3 支持岛**。官方原文："只在 OS3 版本上支持岛" |
| 设备现状 | 小米 15 Pro 出厂为 HyperOS 2，**能否升到 OS3 取决于小米推送计划** |
| 权限 | 用户可关闭焦点通知权限，需通过 `canShowFocus` 查询 |
| 图片限制 | 单张 ≤ 100KB；网络 URL 必须 HTTPS；宽高比 1:1 ~ 16:9 |

**不建议做的理由**：
1. 超级岛面向**持续进行中的实时状态**（充电、打车、导航、外卖、播放）
2. 本项目的灵感速记是**瞬时动作**，没有可持续状态可展示
3. 硬做只能显示静态信息，无法实时刷新，偏离岛的用途
4. 依赖系统版本，随时可能因未升级而不可用

**结论**：系统级入口采用**桌面小组件 + 通知栏按钮**，
「小米超级岛」**排除出范围**。

### 10.2 版本号规则 ✅

版本号形如 **`主.次.修订`**，三段按改动性质从高到低对应：

| 位 | 含义 | 归入该位的改动 |
|---|---|---|
| 第一位（主） | 软件重构 | 结构调整、模块拆分/下沉、流程或接口重做、大范围重写 |
| 第二位（次） | 新功能添加 | 新增能力、新增界面/入口/参数 |
| 第三位（修订） | bug 修复 / 外观修复 | 缺陷修正、文案与提示修正、样式与布局调整 |

**补充约定**：

1. 一次改动同时包含多类时，**按最高位那一类升级**
   （例如「重构 + 新功能」算重构位）。
2. 纯粹的重构、新功能、修复**各自只动对应的一位**，不顺手加其它位。
3. **用户明确指定版本号时以用户为准。**
4. **界面外观类改动一律走修订位**：调整配色、材质、透明度、模糊、圆角、间距、文案，
   以及随之增补的配色预设、参数滑杆，都算「样式与布局调整」，按 `style` 处理升**第三位**。
   - ❌ 不要因为「多了一个滑杆 / 多了一套预设」就当成新功能
   - ✅ 只有新增窗口、新增流程或新增对外入口（例如新增一个设置分区承载全新能力）才升**次位**
   - 例：`3.4.0` 之后的「玻璃材质改为无色 + 新增六套预设」定为 **`3.4.1`**，而不是 `3.5.0`

**与提交类型的联动**：

| type | 升级位 |
|---|---|
| `refactor` | 主位 |
| `feat` | 次位 |
| `fix` / `to` / `style` | 修订位 |

### 10.3 Commit Message 规则 ✅

**结构**：
```
<type>(<scope>): <subject>

<body>

<footer>
```

**① subject（必需）** —— 紧跟 `:` 之后的一行

| 要求 | 说明 |
|---|---|
| 语言 | **中文**（本仓库要求）。"首字母小写"只适用于英文标题，中文不套用 |
| 时态 | 以**动词开头、用现在时**（"添加"、"修复"、"合并"） |
| 禁用 | ❌ "添加了"、"已添加"、"修改了" 等过去式 |
| 结尾 | ❌ 不加句号 |
| 长度 | 不超过 **50 个字符** |
| 内容 | 只描述这次做了什么。忌"修改文件"、"更新代码"、"修复 bug" |

**② Body（可选）** —— 空一行后开始，可多行

- 用**第一人称现在时**
- **必须说明变动动机**，以及与以前行为的对比
- 罗列具体改动时用 `-` 列表

**③ Footer（可选）** —— 只用于两种情况，各占一段

- **不兼容变动**：以 `BREAKING CHANGE:` 开头，写清变动内容、理由与迁移方法
- **关闭 issue**：`Closes #123`（多个写 `Closes #123, #245, #992`）

**合法 type 取值**：

| type | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | **真正解决问题**的提交 |
| `to` | **只推进问题、尚未修完**的中间提交 |
| `docs` | 文档 |
| `style` | 样式 / 外观 / 文案 |
| `refactor` | 重构 |
| `perf` | 性能优化 |
| `test` | 测试 |
| `chore` | 构建 / 工具 / 依赖 |
| `revert` | 回滚 |
| `merge` | 合并分支 |
| `sync` | 同步（与云端或外部对齐） |

> **本项目 scope 建议值**：`project` / `board1` / `board2` / `inspiration` / `task` /
> `ui` / `sync` / `data` / `cloud` / `platform` / `repo` / `docs`

### 10.4 更新日志规则 ✅

**依据**：[Keep a Changelog 中文版](https://keepachangelog.com/zh-CN/0.3.0/)

| 项 | 约定 |
|---|---|
| 文件名 | `CHANGELOG.md`（**大小写照写**） |
| 位置 | 仓库根 `E:\Guide Line\CHANGELOG.md` |
| 顺序 | **时间倒序** —— 最新版本在最上，最旧在下 |
| 日期格式 | **`YYYY-MM-DD`**。❌ 禁止 `2025年9月10日`、`09/10/2025` 等写法 |
| 顶部 | 保留 `## [Unreleased]`。发布时改成版本号并补日期，再加一个新的空 `Unreleased` |

**每个版本必须写明日期，条目按以下英文分类归置**：

| 分类 | 含义 |
|---|---|
| `Added` | 添加的新功能 |
| `Changed` | 功能变更 |
| `Deprecated` | 不建议使用，未来会删掉 |
| `Removed` | 之前不建议使用的功能，这次真的删掉了 |
| `Fixed` | 改的 bug |
| `Security` | 改的有关安全的 bug |

**其它要求**：

- 空的分类**直接删掉**，不要留空标题占版面
- 更新日志**不是 git 日志的堆砌** —— 只记最重要的变更，写给人看（说人话）
- 因安全或重大 bug 撤下的版本，标题后标 `[YANKED]`（大写、方括号）
  例如：`## [0.0.5] - 2014-12-13 [YANKED]`

**三条禁忌** ❌：

1. 把 git 日志直接倒进更新日志
2. 删功能却不先写 `Deprecated`
3. 用各种不靠谱的日期格式
