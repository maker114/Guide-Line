# 开发节奏

这份文件只回答一件事：**为什么一个版本的迭代要花掉一个多小时，以及下一批怎么把它压下来。**

它不是感想，是从 git 提交时间戳和 `.tools/diag/` 里每个产物文件的修改时间**量出来**的。
下次动手前先看一遍第 4、5 节。

---

## 1. 实测基线（本机 Flutter 3.47.5）

| 命令 | 墙钟耗时 |
|---|---|
| `flutter analyze --no-pub`（全量） | **6.3 秒** |
| `flutter test test/ui/xxx_test.dart --no-pub`（单文件 3 例） | **6.5 秒** |
| `flutter test --no-pub`（全量 177 例） | **9.3 秒** |
| `flutter build apk --release` | ~50 秒 |

> ⚠️ **注意第 2、3 行**：跑全量 177 例只比跑 3 例多 **2.8 秒**。
> 所以「少跑点测试」几乎省不下时间 —— 别往这个方向优化。
> 真正贵的是**发起一次调用的回合**，不是命令本身。

## 2. v1.1.0 那一批的实际情况

| 指标 | 数值 |
|---|---|
| 墙钟跨度 | **2.75 小时** |
| 提交数 | 13 个（其中 4 个是发版 / 文档） |
| 平均每个提交 | **13.8 分钟** |
| 截图 | 26 张 |
| `flutter analyze` | 34 次 |
| `flutter test` | 35 次 |
| release 构建（含装包） | 7 次 |
| 模拟器启停 / 装包 | 8 次 |

把这些命令的实测耗时加总：

```
34 × 6.3s  (analyze)   ≈  3.6 分钟
35 × 9.3s  (test)      ≈  5.4 分钟
 7 × 70s   (构建+装包)  ≈  8.2 分钟
 8 × 60s   (模拟器)     ≈  8.0 分钟
26 × 5s    (截图)      ≈  2.2 分钟
                        ───────────
                         约 27 分钟
```

**165 分钟里，命令本身只占约 27 分钟。** 剩下的全在回合周转上：
一次工具调用 → 等结果 → 推理一轮 → 再下一次调用。

### 所以「一版超过一小时」的算式是

```
8 个功能项 × 每项约 14 分钟 ≈ 110 分钟
+ 发版与文档              ≈  20 分钟
+ 中途问答往返            ≈  若干
─────────────────────────────────
                        ≈ 2.75 小时
```

**不是某处卡住，是「项数 × 每项的往返次数」。**

## 3. 根因：用最贵的手段验证最便宜的结论

一条截图验证链是 3~4 个回合：点一下 → 睡 2~3 秒 → `screencap` → `adb pull` → 读图 → 决定下一步。
26 张截图 ≈ **80~100 个回合**，占掉这批的大部分周转。

对比一下同批次里**做对了**的那件事：

> 交互流程 `test/ui/task_link_next_test.dart`：写它约 2 分钟，跑一次 6.5 秒，
> **一次就抓到了「接一条新后续会把原有走向整条覆盖」这个截图怎么点都发现不了的 bug**
> —— 靠截图只能看到"支路数量没变"，看不出边被覆盖。

反面对照（我自己的两次浪费）：

- 动作面板里把「接后续任务…」的 y 坐标量错：一次点到「重命名」，一次点在遮罩上把面板关掉，
  **每次都白跑一整个截图循环**；
- 已经用测试证明了修复，又花十几分钟在模拟器上像素点击复验一遍 —— 第二次只是在证"渲染没崩"，
  一次截图就够，用了十几次。

## 4. 验证手段选择表（照这个选，别凭手感）

| 要验的东西 | 用什么 | 不要用 |
|---|---|---|
| 规则、算法、数据模型 | `test/core/*` 纯逻辑测试 | 截图 |
| 界面接线：点得到吗、建出数据了吗、状态变了吗 | `test/ui/*` widget 测试 | 截图 |
| 布局溢出、字号放大、深浅色 | widget 测试里设 `tester.view.physicalSize` + 文本缩放 | 真机手点 |
| **好不好看**（配色、间距、徽标是否好读） | **截图，每个功能最多 1 张** | 反复截图 |
| 真机专属行为（IME、启动路径、升级后数据） | Intent + `dumpsys`（见《构建与发布》§6.1） | 无（adb 注入被拒） |
| 发布包本身能用 | 发版前装一次真机 | 每改一处装一次 |

**一句话：逻辑用测试证，外观才截图，一批只上一次设备。**

## 5. 每一批的动作节奏

### 开批前（一次问清，省掉后面的往返）

- 需求里凡是**有二义**的地方一次问完：模型怎么定、要不要做、做到什么程度、推到哪。
- 本项目的教训：v1.1.0 的 ③④⑤⑧ 都是做到一半才确认的，
  其中「按项目分组」的确认发生在**发版之后**，直接多出一个只改文档的提交和一轮往返。

### 实现中

- **一个文件一次读完**（别切成 4~5 段读，一段一个回合）。
- **一组相关改动一次改完**，再跑一次测试；不要「改一行 → 跑全量 → 再改一行」。
- 逻辑与接线**先写测试**：写测试的 2 分钟会在第一次回归时就赚回来。
- 需要看界面时，先问自己：**这件事测试能不能断？** 能就别截图。

### 收尾（设备走查）

- 测试全绿之后**才**上设备，一批 **1~2 次**，不要每改一处构建一次。
- 一条命令串起整轮：`build && install && launch && screencap && pull`，
  不要拆成 4 次调用。
- 走查只为回答「观感对不对」，**不承担逻辑验证**。

### 版本与日志（**随功能改动走，不单独一轮**）

- 版本号与 `CHANGELOG.md` 新增的那一节**跟功能改动放在同一个提交**里
  （当前口径：一个小版本对应一个提交）。落点漏一个，`test/core/version_test.dart`
  与 `test/core/docs_consistency_test.dart` 就会红。
- 口径见 `AGENTS.md` §6 / §8。

### 发版（独立一轮）

打 tag + 出包 + 发 Release，约 4 分钟，别和功能实现混在同一轮里。
流程见《构建与发布》§7（`v1.5.2`~`v1.5.5` 的 tag 待补也记在那里）。

## 6. 量化目标（下一批照这个自检）

| 项 | 目标 |
|---|---|
| 单个功能项 | ≤ 10 分钟 |
| 8 项一批 | ≤ 60 分钟 |
| 设备走查 | ≤ 2 次 |
| 截图 | ≤ 10 张 |
| `flutter test` 全量 | ≤ 3 次（写完一批 / 提交前 / 发版前） |
| 中途问答往返 | 0 次 |

**没达标时先看这个**：是不是又用截图去证逻辑了？是不是同一件事证了两遍？

## 7. 反模式清单（每条都是真发生过的）

| 反模式 | 代价 |
|---|---|
| 用截图确认「数据对不对」 | 每个结论 3~4 个回合，且看不出边被覆盖这类问题 |
| 同一件事既写测试又截图证一遍 | 白白多花十几分钟 |
| 每改一处就 `build apk --release` + 装 51 MB | 每次 3~4 个回合 |
| 分片读同一个大文件 | 读 5 次 = 5 个回合 |
| 需求做到一半才问 | 一轮往返；问晚了还会多出一个提交 |
| 只看截图判断键盘弹没弹 | 截图看着像弹了其实没有（真踩过） |
| 用 `adb exec-out screencap -p > x.png` | PowerShell 会按文本重写换行，PNG 是坏的 |

## 8. 已经付过、不用再付的一次性成本

第一版（v1.0.0）跨了 35 小时，三段大空档（696 / 481 / 428 分钟）主要烧在环境上。
这些**都已经修好并写进文档**，不会再犯：

- Gradle 发行包下载卡在 0 字节 → 用镜像预置（《构建与发布》§4）
- AVD 放 C 盘空间不够 → `ANDROID_AVD_HOME` 挪到 `E:\android-avd`
- Kotlin 增量编译缓存崩 → `kotlin.incremental=false`（《构建与发布》§5）
- 小米 HyperOS 侧载受限 → 开「USB 安装」
- HyperOS 不给 adb 注入输入事件 → 真机改用 Intent + `dumpsys`（《构建与发布》§6.1）
- 电脑端（Windows）工具链 → 本机已有 VS 2022 的 C++ 桌面工作负载，`windows/` 由
  `flutter create --platforms=windows .` 一次生成，删掉 `ephemeral` 后干净重建也只要约 13 秒
  （《构建与发布》§10）。**没有需要预置的镜像，也没有要手工开的系统开关**

## 9. 也要承认：有些时间不是浪费

- 真正的设计工作是要花时间的：分叉/合流那一项（DAG 模型 + 渲染 + 操作）用了 3 个提交约 41 分钟，
  它是这批里唯一新增了**数据模型**的东西，这个开销是合理的。
- 契约变更（改了字段就必须同步改契约样本 + 规格文档 + 同一个提交）也不能省。

**要砍的是周转，不是思考。**

## 10. 共享工作区里的提交纪律（刚踩过，代价是 100 个文件）

这个仓库可能同时有别的会话 / 人在改，**它们的改动可能已经进了暂存区**，
而 `git commit` 提交的是**整个暂存区**，不只是你刚 `git add` 的那个文件。

真实事故：

- 仓库主人**有意**移除电脑端归档工程 `archive/desktop-v1/`（301 个文件 / 约 263 MB），
  这个删除已经进了暂存区，等着和当批改动一起提交；
- 我 `git add docs/开发节奏.md` 之后直接 `git commit`，
  于是那个提交变成「新增一份文档 **+ 删掉 16000 行归档**」——
  而提交信息里还写着"只提交本文件"，**完全对不上**；
- 万幸还没推送，`git reset --soft <上一个提交>` 撤回，
  再 `git commit -F msg.txt -- <我的文件>` 重做，零损失。

规则：

1. 提交前**先跑 `git diff --cached --name-only`**，确认里面只有你要提交的文件。
   （只看 `git status` 不够：别人的 `git rm` 可能刚好发生在你两次检查之间。）
2. 共享工作区里**永远不要** `git add -A` / `git add .` / `git commit -a`。
3. 只提交自己那一个文件就用带 pathspec 的提交：
   `git commit -F .tools/commitmsg.txt -- <你的文件>`
   —— 它只提交这些路径，暂存区里别人的东西原样留着。
4. 暂存区里出现不是你加的东西：**不要替别人做决定**（既别一起提交，也别替它撤掉），
   先问一句，并在汇报里讲清楚。
5. 提交完立刻 `git show --stat HEAD` 自查：文件数和你的预期一致吗？
6. 没推送之前一切都好办；**先确认 `git ls-remote` 再动手回退**，推送过的就别 reset。

**要点不是"别人删了东西"** —— 那次删除是仓库主人**有意为之**，
错的是我**提交了别人放进暂存区的东西**，而且提交信息与实际内容不符。

## 11. 远端推送只由仓库主人执行

**这是一条硬规则，不因"顺手""保持同步""这批做完了"而放宽：**

- 自动化 / 智能体会话**绝不执行 `git push`** —— 不推分支、不推标签、不推任何大小的改动。
- 远端推送**只由仓库主人手动执行**，或在他**明确下令**之后执行。
  上一轮推过、目标里写着"并推送"，都**不构成**下一次的授权。
- 也不要绕道：不改远端配置、不换协议（SSH / HTTPS）、不改远端地址来"顺手推一下"。
- 需要推送时：**把提交留在本地**，汇报里写清"还有哪些提交没推"，
  附上确切命令，然后**等授权**。

同一约定同时写在四处：`AGENTS.md` 第 1 条（自动化会话的入口）、
《构建与发布》§8（推送流程所在处）、本节、以及 `.gitmessage` 提交模板
（每次写提交信息都会看到）。写这么多处，是因为这一条踩过：

> 仓库主人明确说过"给我命令，我自己同步"，我后来查到他已手动推送过一次，
> 就默认"以后推送都可以由我来"——**这是错的**。一次授权只对那一次有效。
