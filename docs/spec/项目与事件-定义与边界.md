# 项目与事件的定义与边界

> 这份文件回答三件事：**每个词是什么意思**、**谁管什么**、**什么不做**。
> 它不是教程，是口径 —— 界面文案、数据规则、测试命名都以它为准。
> 来源：2026-09-26《GuideLine开发优化》清单的第 1、3、8、14、15 条。
> 相关：字段与取值以 [`数据契约.md`](数据契约.md) 为权威；形状与承载色见 [`界面规范.md`](界面规范.md)。

---

## 0. 一句话

| 东西 | 它是什么 |
|---|---|
| **灵感** | 还没想好归属的一句话 |
| **项目** | 一个目标**及其规划**：为什么做、要什么结果、怎么一步步做 |
| **事件** | 一条**待办清单**：这件事到哪一步了、下一步做什么 |
| **任务** | 清单里的一条，**日期挂在它身上** |

流向一句话：**灵感进来 → 在项目里想清楚 → 在事件里排成一条线 → 在任务上勾掉。**

> 这两条线是**分开**的，不是同一件事的两种视图：
> 项目里的「实现清单」是**规划用的笔记**，事件里的任务是**要执行的待办**。
> 它们之间**没有任何自动联动** —— 这条是刻意定的（见 §2.1、§2.3）。

## 1. 术语表

| 词 | 定义 | 允许这么用 | 不许这么用 |
|---|---|---|---|
| **项目** | 一个目标及其规划 | 写目的（目标视图叫「有什么问题 / 思路」，分类视图叫「总纲领」）、写做法、列实现清单、设日期、设标识色、套下级 | 不把具体待办写进项目（那是事件的事） |
| **分类** | **有下级**的项目，只用来归类 | 起名、给标识色、排顺序、写**总纲领**、展开下级看它的实现清单 | 不写做法 / 实现清单 / 日期，不标完成 |
| **目标** | **没有下级**的项目，真正要交出的结果 | 全套字段都能用 | —— |

> **界面上写「项目」的地方是统称，不违背上面两行**（2026-10-07）：根层那个新建入口
> 叫**「新建项目」**，因为点它建出来的**永远是一个项目** ——「分类 / 目标」是它
> **事后**的角色判据（有没有下级），刚建出来的一行二者都还不是。
> 逐层的动作名照旧随层级走：在分类下新建的仍叫「新建目标」。
| **事件** | 一件事的待办清单（一条任务线） | 加任务、排顺序、设标识色、标三态、归档 | 不写"为什么做"（那是项目的事）；事件自己没有日期 |
| **任务** | 待办清单里的一条 | 到期日、三态、挂子任务 | 不能直接挂在项目下面 |
| **子任务** | 挂在某个任务框里的补充项 | 归属该任务、有自己的一条内容 | 不能有下级（只两层） |
| **灵感** | 还没想好归属的一句话 | 分配到项目、合并、丢弃 | 不是待办，不参与任何完成判定；**没有标签**（2026-09-27 移除，见 ADR-072） |
| **实现清单** | 项目里"要做什么"的列表 | 加、改、勾、排序；长按条目可以「**建成任务…**」 | **不参与完成判定**，与事件里的任务**没有任何自动联动** —— 唯一的出口是那条显式的一次性动作：建成之后两边互不影响 |
| **归档** | "不再需要了" | 项目 / 事件 / 任务都能归档，归档区能找回 | 不等于"完成"；灵感没有归档动作（它只有丢弃 / 合并） |
| **完成** | "这件事做到了" | 只有**事件**与**任务**有 | 项目没有完成态（见 §2.1） |
| **搁置** | 三态之一："不做了，但留着" | 事件与任务都能搁置；**算终态** —— 参与完成判定（父节点可以因此标记完成），也不再进催办 | 不是删除（记录还在）、不是归档（归档是"暂时不看了"）；**项目没有搁置态**（见 §2.1） |
| **删除** | 让一条记录从主视图消失，分两种 | **项目 / 事件 / 任务**的删除进回收站、30 天内可找回；**灵感**的删除不进回收站，只能靠备份与历次导出 | 不把"删除"说成"彻底删除"（后者才不可逆）；不说"灵感删了去回收站找" |
| **回收站** | 归档区里的一个分区，只装**项目 / 事件 / 任务** | 列出**级联根**（删一个项目就只列那一个项目）；恢复连同级联进来的后代一起回来；保留 30 天 | 不装灵感（它是扁平实体）；它不是"彻底删除"的入口 —— 彻底删除不可逆，必须单独确认 |
| **待办** | **只指事件里的任务** | 说"待办"时指事件里的任务、一条任务线、「全部任务」页里的那些任务 | 项目里的东西叫**清单 / 条目**，不叫待办；灵感更不是待办 |

> **文案已改**（2026-09-26 落地）：项目的「目的」已改称**"有什么问题 / 思路"**、
> 「实现计划」已改称**"如何解决"**；界面、设置页说明与发给模型的提示词三处口径一致。
>
> **分类的同一个字段叫「总纲领」**（2026-09-27 实机反馈）：分类里装的是同一个方向上的
> 几件事，这个方向理应有一句总纲 —— 数据上仍是 `purpose` 一个字段，只是分类视图换了
> 标题与提示语。原来的「汇总」卡（含 N 个目标 / 清单 x/y）已删：数字挂在下级行上，
> 需要时一眼看得到，不必占着首屏。

### 1.1 归档区的三档（2026-09-27 定稿）

归档区**只有三档**。原先把灵感拆成「已丢弃」「已合并」「被隐藏」三个页签，
三档常常各是 0 条却各占一格，手机上要横向滚才看得全 —— 对用户来说那本来就是
同一件事："我手上不再处理它了"。合并成一档、**逐条打来源标记**，
三者的出路仍然各不相同，所以标记必须看得见。

| 档 | 收什么 | 每条的标记 | 出路 |
|---|---|---|---|
| **已归档** | 项目 / 事件 / 任务里 `archived` 且是**级联根**的 | 无（就是"归档"这一件事） | 取消归档（双向级联） |
| **已处理的灵感** | 被隐藏 + 已丢弃 + 已合并 三种灵感 | `被隐藏` / `已丢弃` / `已合并` 三个小胶囊 | 前两者「恢复为待处理」；被隐藏的去取消归档那个项目；已合并的恢复**不回滚项目内容**。**丢弃 / 合并只留 30 天**（2026-10-07 起），被隐藏没有保留期 |
| **回收站** | 项目 / 事件 / 任务里 `deleted` 且是**级联根**的 | 倒计时（还有 N 天自动清除） | 恢复（按级联算，不按列表算）；「彻底删除」不可逆 |

两条边界：

- **灵感删除不进任何一档**（它是唯一不进回收站的实体，见 §8）；删除只留一条墓碑；
- **「被隐藏」不是一种"处理"**，它是算出来的：所属项目一归档，那些待处理灵感
  就从灵感列表里消失。所以它在合并后的那一档里**没有「恢复为待处理」这个动作**
  —— 能改变它状态的只有"取消归档那个项目"。

## 2. 实体的边界

### 2.1 项目

**有**：标题、目的（目标视图「有什么问题 / 思路」、分类视图「总纲领」）、实现计划、
实现清单、日期、标识色、下级项目、归档。

**没有「完成 / 搁置」**（2026-09-26 决定）：

- 项目只表达**"要 / 不要"**：不需要了就**归档**。想表达"这件事做完了"，说到它的**事件**上去。
- 于是"父项目什么时候算完成""父项目为什么还不能完成"这类问题**整体消失**。
- 早先设想的"父项目看最底下的目标是否都终结"（方法甲）**随之作废** —— 没有完成态，就不需要判定。
- 老数据里已经标过完成 / 搁置的项目：**标记原样保留、界面不再显示、也不再产生新的**
  （与"历史枚举值只读保留"同一套做法，**零迁移**，不升 `schemaVersion`）。

**层级与角色**：

- 层级 ≤ 3（根 = 1），这条不变。
- 角色只看一条：**有下级 = 分类，没有下级 = 目标**。规则递归适用、与深度无关 ——
  「工作」（下面全是目标）自己就是分类，「发布 v1」（没有下级）就是目标。
- 分类回答"归哪一类"与"这一类一起往哪走"（总纲领），目标回答"要交出什么"。
- 分类页**只有一个输入框**（总纲领）+ 下级列表（2026-09-27 实机反馈）：下级行可以
  就地展开，展开后能直接看到并**勾选**那个下级的实现清单 —— 在这一层看的是"方向走到
  哪了"，改字 / 删条目 / 建成任务仍旧在下级自己的详情页里。分类**不设日期**，
  所以分类页连日期图标都不给（`showDate: false`），但 `purpose` 与目标是同一个字段。

**明确不做**：不装待办（待办在事件里）、不参与完成判定、不做"按项目分组的任务视图"
（任务在数据上属于事件，要支持它得先给任务加项目字段 —— 那是另一件事，不在本次范围）。

### 2.2 事件

**有**：名字、三态（未完成 / 已完成 / 已搁置）、标识色、一条主线任务链 + 子任务、归档。

**没有**：日期、描述、下级事件（历史裁定仍然有效）。

- 一条事件 = 一条线 = 一件事。想表达"两件事并行推进"，就**开两个事件**。
- 事件的"完成"是**算出来的**：所有参与判定的主线任务都终结（已完成 / 已搁置）时，才可以标记事件完成。
- 首页与详情对同一个事件的进度**必须用同一套数法**（见 §5）。

### 2.3 任务

**有**：标题、到期日、三态、子任务、所属事件。

- 归属唯一：每条任务属于**且只属于**一个事件。
- 一条事件下 `parent_task_id` 为空的任务按顺序依次往下走，就是"接下来做什么"的顺序；
  每个节点还能挂若干子任务 —— 就这两层，没有第三种关系。
- **不做**：不能直接挂在项目下（要有待办，先有事件）；项目实现清单里的**条目不是任务**。

### 2.4 灵感

**有**：正文、归属项目、三种状态（待处理 / 已合并 / 已丢弃）。
（契约里还留着 `tags` 字段，那是**只读保留、零迁移**的历史字段 —— 界面既不产生也不显示，
见《数据契约》§3.1.1 与 ADR-072。）

- 合并到项目时有**三个落点**，每个落点只动一处：手改「如何解决」的正文 / 把原文原封不动
  另起一行追加到正文末尾 / 作为「实现清单」的新一条。前两个落点走「保存」，第三个是一按即成的单独动作。
- **不做**：不参与完成判定；**删除不进回收站**（回收站只装项目 / 事件 / 任务），删了就是删了。

## 3. 想表达什么，就用什么

| 你的意思 | 该用什么 |
|---|---|
| 两件事并行推进 | 开**两个事件**（一条线一件事） |
| 一件事下面有两个并行的要点 | 同一个节点下挂**两条子任务** |
| 调整先后 | 任务动作里的"往上挪一格 / 往下挪一格" |
| 同一类事情放一起 | 建一个**分类**（有下级的项目），把目标挪进去 |
| 这件事不做了 | **归档**（不是删除，也不是"完成"） |
| 这条灵感还没想好 | 留在灵感页或归到某个项目下，别急着变成任务 |
| 清单里的一件事要真的去做 | 长按那条清单条目 →「**建成任务…**」选一条事件（**一次性**：建成后清单与任务互不影响） |
| 把两件并行的任务调成一条线 | 主线节点用「往上 / 往下挪一格」；要换层用「改归属…」（跨事件挂靠不支持 —— 跨事件移动时父引用会归零） |

## 4. 完成规则（只对事件与任务）

1. **可以标记完成 ⟺ 它所有"参与判定"的直接子节点都处于已完成或已搁置。**
2. 墓碑（已删除）与已归档的节点**既不阻塞、也不满足**。
3. 方向不对称：**自动"退回"允许，自动"完成"禁止** —— 把子节点退回未完成，已完成的父节点要跟着退回。
4. 还有未处理的子任务时，父任务的勾选**锁住并说明原因**（不是点了才报错）。
5. **项目不在此列**（见 §2.1）。

## 5. 数量口径

同一件事在不同页面必须**同一个数法、同一种写法**。现状是事件卡写「主线 3/5」、
详情写「主线 3/5 已完成」，而且分子分母的口径还不一样（一个把已搁置算完成，另一个不算；
一个把已归档算进总数，另一个不算）—— 这属于缺陷，不只是措辞问题。

**权威口径见《界面规范》的数量口径一节**（[`界面规范.md`](界面规范.md)）：
数字表只在那里维护一份，本文档不重复抄一遍 —— 抄两份，早晚两处说法打架。

## 6. 常见说错的话

| 说法 | 为什么不对 | 该怎么说 |
|---|---|---|
| "项目里的任务" | 项目不装任务 | "事件里的任务"／"项目清单的条目" |
| "这个项目完成了" | 项目没有完成态 | "这个项目归档了" |
| "事件归档了就是完成了" | 归档是"不做了 / 不看了" | 完成是三态里的"已完成" |
| "灵感删了去回收站找" | 灵感不进回收站 | "灵感删除不可找回" |
| "清单勾完，项目就完成了" | 清单不参与判定 | 项目的收尾方式是**归档** |
| "给这个分类标个完成" | 分类不完成 | 这一类不做了就**归档** |

## 7. 数据影响

- **不新增、不删除契约字段**；`Project` 的 `status` / `completed_at` 转为
  **"只读保留、不再产生"**：老数据读入→写出**逐字节不变**，新建项目写默认值。
- **不升 `schemaVersion`**，老文件不需要迁移。
- 界面侧要跟着改的：项目上的状态胶囊、项目状态图标、"父项目为什么还不能完成"的提示、
  以及依赖项目完成判定的用例。

### 7.1 保存与备份的口径

**数据变更与备份留档是两件事，不要混成一件事说：**

- **数据变更即时落盘**：单个动作一发生就写主文件（原子替换），防断电、防杀进程 ——
  不攒批、不等离开页面。
- **备份在一段编辑会话的「第一笔写入之前」留一份**：推开一个页面就是一段会话。
  同一段会话里的连续保存**不再各留一份** —— 否则改得越勤，老备份被挤掉得越快。
  这一份留的是**进这个页面之前**的状态，所以它的含义是"这一整段操作之前的存档"。
  轮转**刻意不放在会话结束时**：那样一旦"改了一堆、还没退回外壳就断电或被杀进程"，
  这段会话就一份备份都没有。推迟到第一笔写入还有个好处 —— 进了页面什么都没改就退出，
  不会白白占掉一个备份位。不在编辑会话里的散点保存按 5 分钟最小间隔节流。
- **备份列表必须看得见"这一份是什么时候的、里面有多少条"**；日快照不给删除按钮，
  滚动备份可以单独删，但**至少保留一份**。

## 8. 删除与找回对照表

"删掉的东西去哪了、还能不能回来"**只有这一张表说了算**。它必须与代码一致，
界面文案也必须照着它写。

| 实体 | 删除后去哪 | 能不能找回 | 多久失效 |
|---|---|---|---|
| **灵感**（单条 / 批量） | 无去处 —— 回收站**不收灵感** | **不能**（只能靠备份与历次导出） | 墓碑在文件里留 **30 天**，之后骨架化 |
| **项目** | 回收站（只列**级联根**） | 能，**连同子项目**一起回来 | 30 天 |
| **事件** | 回收站 | 能，**整条任务线**一起回来 | 30 天 |
| **任务 / 子任务** | 回收站 | 能，**连同下级子任务**一起回来 | 30 天 |
| 项目下的**未处理灵感**（删项目连带） | 无去处 | **不能** | 30 天后骨架化 |
| **已合并灵感**（所在项目被删） | 退回「未分配」的**待处理** | 内容没丢，但它**不会**在项目恢复后自动挂回去 —— 要挂回去得重新分配 / 合并 | 无 |
| **归档**（项目 / 事件 / 任务） | 归档区「已归档」 | 能（**双向级联**：归档与取消归档都连同下级） | 无 |
| **丢弃的灵感** | 归档区「已处理的灵感」，行上标「已丢弃」 | 能（恢复为**待处理**） | **30 天**（2026-10-07 起；到期同样只留一条墓碑） |
| **已合并的灵感** | 归档区「已处理的灵感」，行上标「已合并」 | 能撤销，但**不回滚项目内容**（写进项目正文的那一行 / 那条清单不退回） | **30 天**（2026-10-07 起；同上） |
| **因项目归档而看不见的灵感** | 归档区「已处理的灵感」，行上标「被隐藏」 | 能（**取消归档那个项目**即可回到灵感列表） | **没有保留期** —— 它只是被遮住，原文一个字没动 |
| **彻底删除** | 骨架化，仍留在原文件里 | **不能** | 立即 |
| **滚动备份**（最近 10 份） | 「备份与恢复」的备份列表 | 能，且可**单独删除**一份（至少留一份） | 被后续保存挤掉之后不能 |
| **日快照**（最近 7 天） | 同上 | 能恢复，但**不给删除按钮** | 自动裁剪（超过 7 天） |

> **界面上任何一句"可以恢复"都必须与本表一致。**

- **灵感是唯一不进回收站的实体**：界面上写"灵感删了去回收站找"就是错的（见 §6）。
- **"不处理了"有三条不同的路，保留期也不同**：丢弃 / 合并**只留 30 天**（2026-10-07 起，
  与回收站同一时机在启动时清，清法与墓碑一样是**骨架化**），而"被隐藏"根本没有保留期
  —— 它不是一种处理，只是所属项目归档之后暂时看不见。
- **"未处理灵感"按"是否已合并"判定**：包括已经丢弃、但还没恢复的那一些 ——
  项目一删，它们同样是只留 30 天的墓碑。
- **"级联根"是列表口径，不是恢复范围**：删一个项目，回收站只列那一个项目，
  但恢复时子项目一起回来 —— 恢复范围永远按级联算，不按列表算。

## 9. 什么情况必须主动告诉用户

原则：**会丢东西、会缩水、会"看起来没事其实少了"的操作，不能指望用户自己发现。**
下面这些不是"可以提示"，是**必须提示**：

| 时机 | 必须说清什么 | 为什么 |
|---|---|---|
| 启动时清理了过期的回收站与已处理的灵感 | 清掉了几条、它们本来属于哪一类（回收站 / 已处理的灵感，两者都只留 30 天） | 用户什么都没做，数据却少了 —— 不吭声就是"静默丢数据" |
| 导出 | **没分享出去不算导出** | 文件只落在应用私有目录，卸载即消失；对着一个没送出去的文件记"已导出"，等于骗人 |
| 主文件损坏、已从备份自动恢复 | 恢复来源（用了哪一份备份）与隔离文件在哪，而且要**能点开看到** | "自动恢复成功"只说明这次没丢；用户得知道少没少，并顺手先导出一份 |
| 导入（整体替换） | 并排列出"当前 N 条 / 文件 M 条 / **将减少 K 条**" | 只列文件里有什么，用户看不出会少掉多少；导入**不是合并** |
| 覆盖性操作之后（导入、恢复备份、AI 覆盖正文等） | 一句"想反悔要尽快" | 备份会被后续保存一轮轮挤掉（滚动只留 10 份），退回的窗口很短 |

> 这一节**只定口径**：什么情况必须说、必须说清什么。
> 具体怎么实现、落在哪个文件、做到哪一步，不属于本文件的职责 ——
> 各条的现行落点与状态查 [`docs/决策索引.md`](../决策索引.md) §2.2。

## 10. 两条联网边界

这个应用只有**两处**会联网，边界都逐条写死：发出去每一个字、凭据存在哪，都以本节为准。
两处的**量级完全不同**——AI 只发一个项目的清单文本，GitHub 同步发的是**整份数据**——
所以第二处默认关着，且只能手动触发。

### 10.1 AI 整理

**这一处的联网口径**：发出去每一个字、密钥存在哪，以本小节为准。

| 项 | 口径 |
|---|---|
| 请求发到哪 | 只有用户自己填的 `baseUrl`（默认 `https://api.deepseek.com`） |
| **发什么出去** | 两条路各发各的：**整理成正文**那一条发「项目标题 + 有什么问题 / 思路 + 未完成的清单条目 + 一段固定提示词」；**拆成清单条目**那一条发「项目标题 + 有什么问题 / 思路 + 「如何解决」正文原文 + 另一段固定提示词」 |
| **不发什么** | 灵感原文、事件与任务、其它项目、导出记录、设备信息 —— 一律不发 |
| 凭据存哪 | `apiKey` **只**存系统安全存储（Android Keystore）；不进 `ui_prefs.json`、不进备份、不进整库导出 |
| 非敏感配置 | `baseUrl` / `model` 进 `ui_prefs.json`（与背景图种子同一个性质） |
| 落盘 | 提示词与模型返回的**原文都不落盘**；只把用户确认后的结果写进 `implementation` |
| 开关 | 默认**关**；没配置 `baseUrl` / `apiKey` 时，界面上的 AI 入口显示「未配置」 |
| 超时与失败 | 超时 30 秒；失败给可读文案（连不上 / 密钥不对 / 额度或限流），**不留半截状态** |
| 呈现 | 结果先给**预览页**，可编辑，确认后才写回 `implementation`；不直接覆盖现有正文 |
| 读取失败 | 安全存储读不出来一律当「未配置」：不抛错、不崩界面 |
| 界面必须说明 | 预览页顶部写明「模型可能补充或改写你没写过的东西，请逐句核对后再写入」（末词与按钮文案一致：拆条目那一路的按钮是「写入清单」） |

### 10.2 GitHub 备份同步（正式功能）

把整份数据推到**用户自己的** GitHub 私有仓库，或从那儿拉回来。请求只发往
`api.github.com`，仓库由用户填，应用不预设任何自己的中转服务。

| 项 | 口径 |
|---|---|
| 请求发到哪 | 只有 `https://api.github.com`：内容走 `/repos/{owner}/{repo}/contents/{path}`，提交码走 `GET /repos/{owner}/{repo}/commits?path=…&sha=…&per_page=1`，「测试连接」另走一句 `GET /repos/{owner}/{repo}` 证明仓库在不在（ADR-090）；`owner` / `repo` / 分支 / 路径全部由用户填 |
| **发什么出去** | **整份数据（`ExportCodec.encode` 的同一份字节，`.json.gz`）+ 一句提交信息 + Token** |
| **不发什么** | 背景图、导出目录里的历史导出、Token 之外的任何本地文件、设备信息 —— 一律不发 |
| 凭据存哪 | Token **只**存系统安全存储；不进 `ui_prefs.json`、不进备份、不进整库导出（与 `apiKey` 同一条硬约束） |
| 非敏感配置 | `owner` / `repo` / `branch` / `path` 进 `ui_prefs.json` |
| 加密 | **不加密**：安全边界是"用户自建的私有仓库"，不是内容加密。界面必须写明这一点 |
| 触发方式 | **页面上手动，开关开着时自动**：页面有「推送」「拉取」两个按钮；开关开着（默认关）时**每次启动静默比对一次**（不画转圈，不一致才摆面板），**回到主页时只在这一趟真的改过数据之后才上传**，**从不自动拉取** —— 云端更新、两边都改过、本机 0 条活记录都只把原因摆出来，交给人到同步页决定（ADR-091 / ADR-093） |
| 覆盖性 | 推送**覆盖**远程那一份（每次提交一份，仓库历史即旧版）；拉取**整体替换**本地，替换前强制轮转备份 |
| 冲突 | 两边都改过时**不自动合并**，只让用户手动三选一：覆盖远程 / 用远程覆盖本地 / 取消；**云端的提交码与上次同步记账里的那一枚相同 ⇒ 这中间没有第三方改过**，此时本机直接覆盖云端、不再多问一遍（自动与手动同一套判据，ADR-093） |
| "0 条不算可用备份" | 远程那份解出来 0 条活记录时**不许拿来覆盖本地**，与本地备份列表同一判据 |
| 版本凭证 | 界面与记账摆出**提交码**（前 7 位）；内容码并列但要分开说明 —— 提交码相同才是"同一次上传"（ADR-089）；老记账没有这一项时写「未知」，不判成"不一致" |
| 开关 | 默认**关**（缺键即关）；关掉不清 `owner` / `repo` / Token，也不删远程那份；关着时入口仍在、只显示「已关闭」 |
| 超时与失败 | 超时 30 秒（读一份大备份时按体积放宽：10 KB/s 打底、5 分钟封顶）；401/403/404/409/422/5xx 各有可读文案（404 会提示"私有仓库用错 Token 也显示 404"），**不留半截状态**；文件涨过 1 MB 时 Contents API 只回空 `content`，改走 `GET /repos/{owner}/{repo}/git/blobs/{sha}` 把内容读回来（普通 JSON 请求、内容是 base64），超过单文件 100 MB 上限则单列一条"太大、请到仓库网页手动下载"（ADR-090） |
| 呈现 | 推送前确认；拉取前先预览**远程条数、时间与提交码**并再确认一次；**四种覆盖式操作（推送 / 拉取 / 从文件导入整体替换 / 合并导入）在真有差别时先摆差异面板**（新增标绿、删除标红、**改写标黄**），没差别就走原来那条确认；备份与恢复里点开某份备份同样先摆这张面板（ADR-092）；改写那两行底下写明**改了什么**（`状态：未完成 → 已完成` 这样的"字段：旧值 → 新值"，每行最多两条，多的写"等 n 处"；`updated_at` 这类必然跟着变的键不报，界面也不编假说明）（ADR-093）；**启动静默比对发现不一致**时摆同一张面板，按钮只有两个 —— 「覆盖云端数据」（本机推上去）/「使用云端数据」（云端拉下来换掉本机），两个都会改数据，所以这扇面板**点空白关不掉**，返回键 = 没选 = 只把那枚黄胶囊留在右上角（ADR-093） |
| 连不上 GitHub | 启动那次静默比对连不上时：右上角画一枚**黄色「GitHub 未连接」胶囊**（常驻到下一次同步成功），并弹一次"继续编辑可能与云端产生差异"的警告；点过「知道了」之后**当天不再弹**，胶囊照常留着（ADR-093） |
| 读取失败 | 安全存储读不出来一律当「未配置」：不抛错、不崩界面 |

三条硬约束（测试逐条钉住）：

1. `ai_config` 的敏感值**只在安全存储里**，偏好 JSON 里连键都不出现；
2. 「更多 → 导出」的整库导出**不含** `apiKey`（它不在数据文件里，天然不含）；
3. 安全存储读取失败**当作未配置**，不抛错。

GitHub 那一处另有两条：

4. GitHub Token 同样**只在安全存储里**，偏好 JSON 里连键都不出现；
5. 远程那份 0 条活记录时**不能被拉下来覆盖本地**（与"0 条不算可用备份"同一判据）。

> AI 覆盖正文、以及拉取远程覆盖本地，都属于覆盖性操作，必须先留一份可退回的旧版（见 §9）。

## 11. 交接说明导出

把**一个**项目导出成一份 Markdown，丢给电脑上的 AI 去实现。**不做多选** ——
一次交代一件事，读的人才抓得住重点。

| 项 | 口径 |
|---|---|
| 入口 | 「更多」或项目详情页 → 选一个项目 → 预览 → 导出为 `.md` |
| 内容顺序 | 项目标题 → 有什么问题 / 思路、标识色、日期、导出时间（**有才写**）→ 实现清单 → 整理后的实现说明 → 待处理灵感。**不写项目状态**（项目没有完成 / 搁置态，写进去只会误导对面，见 §2.1 / Q1）；**不带事件与任务线**（事件与项目之间没有关联字段，实机反馈后去掉） |
| 任务列表 | GitHub 任务列表语法 `- [x]` / `- [ ]`；**已完成也导**（打 `[x]`）—— 读的人要知道"已经做了什么"才不会重复建议 |
| 灵感范围 | 只导 `pending`（已丢弃的不再提，已合并的已经进了正文或清单） |
| 空节 | **整节省略**，不留一堆 `（无）` |
| 预览 | 全文可编辑，用户能删掉不想外发的部分；**导出前不另弹确认框**（预览页本身就是确认环节） |
| 隐私提示 | 预览页底部固定一句「导出后文件会离开这台手机；请确认上面没有你不想外发的内容。」 |
| 通道 | 与 `.json.gz` 导出同一套系统分享，导出记账同样适用（见 §9） |

> 交接说明是**纯导出**：导出的内容不构成任务、不参与任何业务判定，也不会改写数据。
