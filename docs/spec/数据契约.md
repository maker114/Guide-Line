> 依据《双端软件架构设计》v13 的 §2.2 / §4 编写。
> **该设计文档与 ADR 清单已不在工作区**（随电脑端归档工程一起离开，只留在 git 历史里）——
> 本文档的字段表与容错规则是**唯一权威**，正文里的 `ADR-0xx` 编号仅作历史出处，
> 不要照着编号去找那份文档。
> **要查某个 `ADR-0xx` 当初裁定了什么、现在还算不算数**：见 [`docs/决策索引.md`](../决策索引.md) §3

> **本文件是代码必须遵守的唯一契约来源** —— 实体字段、类型、顺序、枚举、容错规则全部以此为准。
> 状态：✅ 定稿（对应设计文档 4.0 ~ 4.12）

## 0. 为什么需要这份文件

设计文档 §2.2 的结论：**两端对同一份 JSON 的理解差异不会报错，只会静默损坏数据**。

虽然 8.1 已裁定单实现 Flutter 双端（ADR-031），但**云函数（Node.js）会在数据通路上出现**，
所以契约风险并未消失 —— 应对方式是两条硬约束：

1. 云函数把 `payload` 当作**不透明 JSON** 存取，不解析业务字段（只读 `version` / `updated_at` / `last_tx_id`）；
2. 本契约 + 序列化回归测试（§7）作为**唯一真源**，任何字段变更必须先改本文件。

## 1. 通用规则

| 项 | 规则 | 违反后果 |
|---|---|---|
| 编码 | UTF-8，**无 BOM** | 中文乱码、比对失败 |
| 换行 | `LF` | 跨端差异 |
| 缩进 | **2 空格**（仅落盘/传输用，比对前不重排） | 逐字节比对失败 |
| key 顺序 | 严格按 §3 字段表顺序写出（Dart 用 `LinkedHashMap` / 显式 `Map` 构造） | 逐字节比对失败 |
| 可空字段 | **必须写出 key**，值为 `null`，**禁止省略** | 语义歧义（缺失 vs 空） |
| 时间戳 | `int64` 毫秒整数；**禁止浮点、禁止字符串**；记录级由客户端生成，文档级由服务端生成（ADR-067） | 精度丢失、排序错乱 |
| 日期 | 字符串 `"YYYY-MM-DD"` 或 `null`；**不涉及时区** | 字段污染、比较失败 |
| 布尔 | `true` / `false` | — |
| UUID | v4，**小写、带连字符** | 记录匹配不上 |
| 枚举 | **小写字符串**（`"standard"`） | 类型字段全乱 |
| 数字 | 只用整数（`order` / 时间戳）；不使用浮点 | `1.735e12` 之类的科学计数 |
| 禁止 | 注释、尾随逗号、`NaN` / `Infinity` | 非法 JSON |
| 中文 | 不转义（Dart `jsonEncode` 直接输出 UTF-8 字符） | 比对失败 |

## 2. 文档外层结构

### 2.1 本地数据文件（**当前形态**：单文件，`schemaVersion: 3`）

手机端（Android 单机）把四类集合放在**同一份文件**里，文件名固定为 `guideline.json`：

```json
{
  "schemaVersion": 3,
  "savedAt": 1788652800000,
  "collections": {
    "projects":     { "items": [] },
    "inspirations": { "items": [] },
    "events":       { "items": [] },
    "tasks":        { "items": [] }
  }
}
```

| 字段 | 类型 | 生成方 | 说明 |
|---|---|---|---|
| `schemaVersion` | int | 客户端 | 当前为 `3`。结构变更时必须递增，读取方**必须保留旧版读取路径**，且拒绝读取版本号高于自己的文件 |
| `savedAt` | int64 | 客户端 | 本次落盘的时间戳；**仅供人看**，不参与任何判定或排序 |
| `collections.<集合名>.items` | array | 客户端 | 该类实体的**全量**记录，含墓碑与墓碑骨架 |

**v2 → v3（破坏性变更，仓库主人明确要求）**

任务表删掉了 `next_task_ids`，连带删掉整套「走向边 / 分叉 / 合流」（见 §3.4.1）。
读取 v2 文件时：

- `next_task_ids` **直接丢弃**，并且**不再透传**（不进 `extra`）—— 否则那个键会跟着
  用户数据永远活下去，等于没删；
- 一条任务线的顺序回到 `order` 这一条链：老数据里分叉出去的那几条，按 `order`
  依次排在同一条线上（不再是支路，也不再有合流点）；
- 其余字段原样读写，**不做任何其它迁移**。

> 这是一次**不可逆**的删除：分叉 / 合流的信息在被保存一次之后就没了。
> 升级前请留一份备份（App 的滚动备份与「导出」都能当备份用）。

**关键约定**

- 集合名固定为 `projects` / `inspirations` / `events` / `tasks`（与 `DocName.key` 一致）。
- **单文件只改外层，不改记录**：`items` 里每条记录的字段、顺序、可空形态仍严格遵循 §3，
  因此 §6 的逐字节样本回归对每条记录依然有效。
- 写入是**原子替换**（写 `*.tmp` → flush → rename）；跨集合的变更（例如合并灵感同时改项目与灵感）
  在一份文件里天然是"全有或全无"，不再需要"待完成事务"。
- 界面偏好（折叠状态、上次页签、上次导出时间）**不是数据**，单独写在 `ui_prefs.json`，
  损坏时静默重置，绝不影响 `guideline.json`。

### 2.2 兼容：v1 四文档信封（**只读**）

电脑端旧版导出的是"一类实体一份文档"的形态，读取方必须仍能读进来：

```json
{
  "version": 42,
  "updated_at": 1735000000000,
  "last_tx_id": "3f2a9c14-8b7e-4d21-9c6a-1e5b7f0a2d33",
  "payload": { "items": [] }
}
```

| 字段 | 说明 |
|---|---|
| `version` / `updated_at` / `last_tx_id` | 原双端方案的**服务端生成**字段，单机版**不再写入**，读到即忽略 |
| `payload.items` | 与 §2.1 的 `items` 同义，直接按 §3 解析 |

导入时若一份文件里出现 `projects.json` 等键（四文档被拼进一个对象），
按兼容路径读入并给出提示。**写入永远只写 §2.1 的形态。**

## 3. 实体字段表

> **字段顺序即写出顺序**。所有字段必填（可空字段写 `null`）。

### 3.1 Inspiration（灵感）→ `inspirations.json`

| # | 字段 | JSON 类型 | Dart 类型 | 约束 |
|---|---|---|---|---|
| 1 | `id` | string | `String` | UUID v4 小写 |
| 2 | `text` | string | `String` | `trim()` 后长度 ≥ 1，禁止纯空白 |
| 3 | `project_id` | string \| null | `String?` | 指向 `Project.id`；未分配为 `null` |
| 4 | `status` | string | `InspirationStatus` | `pending` / `merged` / `discarded` |
| 5 | `merged_into` | string \| null | `String?` | 指向 `Project.id`；仅 `merged` 时非空（见 §4.3） |
| 6 | `merged_at` | int64 \| null | `int?` | 仅 `merged` 时非空 |
| 7 | `created_at` | int64 | `int` | 客户端时间戳 |
| 8 | `updated_at` | int64 | `int` | 客户端时间戳 |
| 9 | `deleted` | bool | `bool` | 软删除标记 |
| 10 | `tags` | string[] | `List<String>` | **可省**：空数组时**不写出**该字段。逐项 `trim`、丢空串、按出现顺序去重，见 §3.1.1 |

> 灵感**没有** `order` / `archived` / `completed_at`；列表按 `created_at` 倒序（设计文档 4.12）。

#### 3.1.1 `tags`（标签）的写出规则

`tags` 是后加字段（灵感整理第 5 条），为了**不破坏既有数据的逐字节形态**，
采用"空即省略"：

- **空数组不写出**：老数据没有这个字段，读进来再写出去必须与原文逐字节一致，
  否则契约样本回归会挂、用户手上的旧文件也会被无谓改写；
- **非空数组按契约的通用格式写出**（每个元素独占一行，与其它数组一致）；
- **位置在已知字段之后**：新字段一律追加在末尾，不打乱既有顺序，这样
  `extra` 透传与字段顺序都不会互相干扰；
- 读取容错（§8）：不是数组 → 记一条 error 并当作空；数组里有非字符串项 →
  跳过该项并记 error，**不让整条记录废掉**。

### 3.2 Project（项目）→ `projects.json`

| # | 字段 | JSON 类型 | Dart 类型 | 约束 |
|---|---|---|---|---|
| 1 | `id` | string | `String` | UUID v4 |
| 2 | `title` | string | `String` | 非空（trim 后 ≥ 1） |
| 3 | `purpose` | string | `String` | 允许空串 |
| 4 | `implementation` | string | `String` | 允许空串；手写、AI 整理、灵感合并（合并编辑器里「保存」那条路）都写这里，见 §3.2.1 |
| 5 | `date` | string \| null | `String?` | `"YYYY-MM-DD"`，截止/目标日 |
| 6 | `status` | string | `NodeStatus` | `pending` / `done` / `ignored` |
| 7 | `archived` | bool | `bool` | 可见性开关，与 `status` 正交 |
| 8 | `parent_project_id` | string \| null | `String?` | 嵌套深度 ≤ 3 层（根 = 第 1 层） |
| 9 | `order` | int | `int` | 同父兄弟排序，间隔 1000 |
| 10 | `completed_at` | int64 \| null | `int?` | `done` 时写入，退回时置 `null` |
| 11 | `created_at` | int64 | `int` | |
| 12 | `updated_at` | int64 | `int` | |
| 13 | `deleted` | bool | `bool` | |
| 14 | `color` | string \| null | `String?` | **可省**：`null` 时**不写出**该字段。标识色，`#rrggbb` 小写 |
| 15 | `items` | object[] | `List<ProjectItem>` | **可省**：空数组时**不写出**该字段。「实现」的待办清单，见 §3.2.1 |

> ⚠️ `collapsed` **不在契约中**（ADR-059）：视图偏好存本地 `ui_prefs.json`，不参与同步。
>
> `color`（标识色，灵感整理第 10 条）与 `items` 同一套规则：**未设置即省略**、
> 位置追加在末尾，保证老数据"读入→写出"逐字节不变。读取时按 `#rrggbb`（小写）
> 校验，坏值置 `null` 并记一条 error；色值口径与 `ui_prefs.json` 的背景种子一致。

#### 3.2.1 `items`（实现清单）

「实现」从一段纯文本扩成**待办清单**（设计文档《实现清单与AI整理》§1）。

| # | 字段 | JSON 类型 | Dart 类型 | 约束 |
|---|---|---|---|---|
| 1 | `id` | string | `String` | UUID v4 小写；**同一项目内不得重复** |
| 2 | `text` | string | `String` | `trim()` 后长度 ≥ 1 |
| 3 | `done` | bool | `bool` | 是否打勾 |

三条必须遵守的约定：

1. **顺序 := 数组下标**。条目**没有 `order` 字段** —— 任务存 `order` 是为了跨父节点
   排序并兼容老数据的隐式链；清单是一维列表，数组顺序就是顺序，再存一个只会多一处
   能不一致的地方。
2. **不参与任何业务判定**。`done` 只表达"打勾了"：完成规则、反向传播、归档级联
   全部只看项目的三态；清单**全勾完也不会**把项目变成 `done`。
   它也与事件里的任务**没有任何联动** —— 联动会出现"项目里勾了、任务线那边没动"的矛盾。
3. **`implementation` 保留**，不删。它是 AI 整理与交接导出的输入，
   也是老数据的唯一存身之处。**灵感合并有两个落点**（2026-09-25 按实机反馈定）：
   合并编辑器里手改正文 / 追加原文后点「保存」→ 写 `implementation`；
   点「作为清单条目」→ 追加成 `items` 的新一条。两条都只动一处，互不牵连。

读取容错（§8）：`items` 不是数组 → 记 error 并按空处理；单个条目坏掉
（不是对象 / 缺 `id` / `text` 为空 / `id` 与前面重复）→ **只跳过该条目**并记 error，
不让整个项目解析失败。条目里出现的未知键照旧透传。

> 写入侧：`text` 为空一律拒绝（`RuleViolation`）并保持原值 —— 与"灵感内容不能为空"
> 同一条约定。`items` 里不会出现空文字条目。

### 3.4 Task（任务）→ `tasks.json`

| # | 字段 | JSON 类型 | Dart 类型 | 约束 |
|---|---|---|---|---|
| 1 | `id` | string | `String` | UUID v4 |
| 2 | `event_id` | string | `String` | 必填，指向 `Event.id` |
| 3 | `parent_task_id` | string \| null | `String?` | **归属**：`null` = 链上的节点；非空 = 挂在某个节点框内的子任务 |
| 4 | `task_type` | string | `TaskType` | `standard` / `subtask` / `parallel`（历史，见 §4.1） |
| 5 | `title` | string | `String` | 非空 |
| 6 | `due_at` | string \| null | `String?` | 到期/目标日，**不联动任何任务** |
| 7 | `status` | string | `NodeStatus` | `pending` / `done` / `ignored` |
| 8 | `archived` | bool | `bool` | 归档任务级联其子任务 |
| 9 | `order` | int | `int` | **链路顺序**：同一事件下 `parent_task_id = null` 的节点按它依次往下走 |
| 10 | `completed_at` | int64 \| null | `int?` | 同 Project |
| 11 | `created_at` | int64 | `int` | |
| 12 | `updated_at` | int64 | `int` | |
| 13 | `deleted` | bool | `bool` | |

> ⚠️ v3 删掉了 `next_task_ids`（走向边）。老文件里那个字段读入即丢弃，见 §2.1 的迁移说明。

#### 3.4.1 一条任务线 = 一条链

事件下 `parent_task_id = null` 的节点按 **`order`** 依次往下走；每个节点可以挂若干
**子任务**（`parent_task_id` 指向它）。就这两层，没有第三种关系。

**为什么删掉「走向边」（分叉 / 合流）**：它当年用来表达"两条线并进、再汇合"，
代价是用户得先学会「支路 / 分叉点 / 合流点 / 走向」这一套概念，还要在手机屏幕上
分辨缩进、支路色与徽标 —— 与「快速理清一件事的脉络」这条初心冲突。

**替代做法**（都在既有概念里）：

| 想表达 | 怎么做 |
|---|---|
| 两件事并行推进 | **开两个事件**（一条线一件事） |
| 一件事下面有两个并行的要点 | 同一个节点下挂**两条子任务** |
| 调整先后 | 动作面板里的「往上挪一格 / 往下挪一格」（交换相邻两个节点的 `order`） |

### 3.5 墓碑骨架（彻底删除后）

`deleted: true` 且其余业务字段被清空，**只保留 3 个 key，顺序固定**：

```json
{ "id": "…", "deleted": true, "purged_at": 1735000000000 }
```

- `purged_at`：int64，客户端时间戳
- 反序列化时**不得**把骨架还原为实体（见 §9）
- 墓碑骨架**仍留在 `items` 中**（ADR-003 不物理删除）

## 4. 枚举与结构约束

### 4.1 枚举值（大小写敏感，全小写）

| 枚举 | 取值 | 适用实体 |
|---|---|---|
| `NodeStatus` | `pending` / `done` / `ignored` | Project / Event / Task |
| `InspirationStatus` | `pending` / `merged` / `discarded` | Inspiration |
| `TaskType` | `standard` / `subtask` / **`parallel`（历史取值，见下）** | Task |

> `NodeStatus` 与 `InspirationStatus` **同名不同义**，**禁止共用一个解析器**（设计文档 4.2.1）。
>
> **`parallel` 已废除**（那套「框内并列」与替代它的走向边都删掉了，见 §3.4.1）：
>   · **只读保留**：老文件里还有这种记录，按 §7「禁止删除枚举值」继续解析，
>     读入后原样写出（**不做迁移**，否则等于偷偷改写用户数据）；
>   · **不再产生**：`Workspace.createTask` / `updateTask` 都拒绝 `parallel`
>     （拒绝理由里指明替代做法：两件并行的事开两个事件，或挂两条子任务）；
>   · 界面上按 `subtask` 渲染（框内一行），交接说明里也标注为「（子任务）」。
>
> 换句话说：**写入侧只有 `standard` / `subtask` 两个活取值**，读取侧有三个。

### 4.2 任务允许的父子组合（ADR-053）

| 父节点 | 允许的**归属**子节点 |
|---|---|
| `Event` | `standard`（`parent_task_id = null`，即链上的节点） |
| `standard` | `subtask` |
| `parallel` | `subtask`（历史类型，只为老数据保留） |
| `subtask` | ❌ 不允许有子节点 |

深度上限：任务树 ≤ 3 层（不含 Event）；项目嵌套 ≤ 3 层（根 = 1）。

> ⚠️ 上表只管**归属**（谁装在谁的框里）。链上的**顺序**由 `order` 决定（§3.4.1）——
> 现在只有这一套顺序语义，不再有走向边。

### 4.3 跨字段一致性（写入前必须校验）

| 实体 | 规则 |
|---|---|
| Inspiration | `status = merged` ⟺ `merged_into != null` 且 `merged_at != null`；其余状态两者必须为 `null` |
| Inspiration | `discarded` / `merged` 的记录 `deleted` 仍为 `false`（合并**不**用 `deleted` 表达） |
| Project | `status = done` ⟺ `completed_at != null` |
| Event / Task | 同 Project |
| Task | `task_type = standard` ⟺ `parent_task_id == null`（链上的节点） |
| Task | `parent_task_id != null` → 父任务必须存在且 `event_id` 相同 |
| Task | 同一事件、同一父节点下的 `order` 必须互不相同（`order` 是顺序的唯一依据） |
| 引用 | `project_id` / `parent_project_id` / `parent_task_id` / `event_id` / `merged_into` 指向的记录必须存在；指向已删除（`deleted`）记录时由上层按设计文档 4.5 / 4.8 的悬挂规则处理 |

---

## 5. 文档分区

单文件里按集合分区（`collections.<集合名>`），**归属唯一**：一条记录只出现在一个集合里。

| 集合名 | 收录实体 | 说明 |
|---|---|---|
| `projects` | Project | 项目树（含嵌套子项目与墓碑） |
| `inspirations` | Inspiration | 灵感全量（含 `pending` / `merged` / `discarded`） |
| `events` | Event | 事件列表 |
| `tasks` | Task | **全部任务**（不按事件拆分） |

> 契约样本仍按"一类实体一份文件"命名（`projects.json` 等）—— 那只是**样本的组织方式**，
> 便于逐条比对记录本身；实际落盘永远是 §2.1 的单文件形态。
> 跨集合变更（合并灵感、删除项目连带灵感）在同一份文件里一次原子写入完成。

## 7. 演进规则

| 变更 | 允许 | 做法 |
|---|---|---|
| 新增字段 | ✅ | 必须**可空或有默认值**；老数据缺失时按默认值补齐；同步更新本契约与本文件版本 |
| 修改字段名 / 类型 | ❌ | 禁止。确需变更 → 新增字段 + 迁移 + `BREAKING CHANGE:` |
| 新增枚举值 | ⚠️ | 需要两端同时支持；旧端读到未知值 → 按降级规则处理（§8） |
| 删除字段 | ⚠️ | 先标 `Deprecated`（CHANGELOG），下一个主位版本才移除 |
| 删除枚举值 | ❌ | 禁止（历史数据仍在） |

## 8. 反序列化容错（必须实现，且必须记录日志）

| 情况 | 处理 |
|---|---|
| 出现未知字段 | 忽略，但**保留原始 JSON**（不因再序列化而丢失）→ 因此实体需带 `extra` 透传区 |
| 缺少已知字段 | 按 §3 的默认值补齐（可空字段补 `null`），记录 `warning` 日志 |
| 类型不符（如时间戳是字符串） | 尝试安全转换；失败则按默认值并记录 `error` 日志 |
| 枚举值未知 | 按降级值处理：`NodeStatus` → `pending`；`InspirationStatus` → `pending`；`TaskType` → `subtask`；记录 `error` 日志 |
| 越界父子组合 | 按 `subtask` 渲染（ADR-053），记录 `error` 日志 |
| 墓碑骨架 | 解析为 `Tombstone`，**不**还原为实体 |
| JSON 整体损坏 | 本地文件：保留现场（重命名为 `.corrupt.<ts>`）并从云端重新拉取；云端不可用时进入只读告警态，**禁止静默重建空数据** |

> 最后一条是**数据安全底线**：宁可只读告警，也不要用空数据覆盖用户的人生记录。
